# smithable.yml — spec version 0.1

`smithable.yml` describes **what** an application does, in technology-neutral terms. This page is the complete reference for version 0.1, together with its companions [`smithable.auth.yml`](#smithableauthyml-sign-in-roles-and-what-is-public) (required) and [`smithable.content.yml`](#smithablecontentyml-visible-text) (optional), and [`smithable.ux.yml`](#smithableuxyml-how-the-app-looks) (optional). Later versions add more.

Check a spec with `smithable validate`. For autocomplete and checking in your editor (VS Code with the YAML extension, or any editor using yaml-language-server), start the file with:

```yaml
# yaml-language-server: $schema=https://docs.smithable.ai/schema/smithable-0.1.json
```

The companion files have schemas of their own: [smithable-auth-0.1.json](https://docs.smithable.ai/schema/smithable-auth-0.1.json), [smithable-ux-0.1.json](https://docs.smithable.ai/schema/smithable-ux-0.1.json), [smithable-content-0.1.json](https://docs.smithable.ai/schema/smithable-content-0.1.json) and [smithable-context-0.1.json](https://docs.smithable.ai/schema/smithable-context-0.1.json), each started the same way. They say what may stand where; `smithable validate` is the judge of the rules between the files.

The [JSON Schema](https://docs.smithable.ai/schema/smithable-0.1.json) covers `smithable.yml`; the companions are checked by `smithable validate`. The files are changed through operations, not by hand: the [operations reference](https://docs.smithable.ai/operations.html) lists every one, generated from Smithable itself.

## Example

```yaml
smithable: 0.1

app:
  name: Acme CRM
  description: Lightweight CRM for a small B2B sales team.
  currency: EUR
  timezone: Europe/Mariehamn

models:
  Customer:
    description: A company we have a commercial relationship with.
    fields:
      name: string!
      email: email unique
      segment: smb | enterprise | government
      creditLimit:
        type: money
        min: 0

pages:
  customers:
    intent: Find a customer quickly and keep their details current.
    crud: Customer

navigation: [customers]
```

## `models`

Model names are PascalCase (`Customer`, `InvoiceLine`). Each model has `fields` (at least one) and may have [semantic text](#semantic-text).

Every model automatically has `id`, `owner` (the user who created the record, when users sign in), `createdAt` and `updatedAt`. These names cannot be declared, and no model may be called `User`: that is the people who sign in.

`smithable validate` warns when a field's name looks like data an app should not hold, or should hold only with great care: a payment card's number, security code or expiry (`card-data`: take payments through a payment provider and keep its reference), a password, key or token (`secret-field`: sign-in is the app's own, and keys for other services belong in the environment), a national identity or passport number (`identity-number`), and health or another specially protected kind of personal data (`special-category-data`). The warning goes by the name alone (a library card's number or a machine's health is not flagged), so whether it is right is yours to judge. `smithable validate --json` prints every finding with its code, file, line and column as one JSON document (`{ valid, diagnostics }`), for a program that acts on them.

| Key | Meaning |
|---|---|
| `fields` | The [fields](#fields) (below) |
| `namedBy` | What names a record, its title wherever one record is shown or referred to ([design/record-names.md](../design/record-names.md)): a field (`namedBy: company`: a text, a choice, a date, a number or an amount), a reference (`namedBy: session`: that record's own name), a field one reference away (`classType.name`), or a list of such parts joined with " · " (`[classType, startsAt]`: "Hatha · Mon 19 Oct, 08:00"), empty parts left out. A name that would come back to itself through references is refused. Left out, the title is picked by rule: the first short text field, else the first long text, else the record's number |
| `ownedBy` | A `User` field whose user owns the record instead of its creator, e.g. `ownedBy: accountManager`. Left empty on a new record, it is the creator. On a change the field keeps what is given, and left empty it stays empty: a record with no one in it is changed only by roles with write on the model, and neither a form nor an action takes it for whoever makes the change; `setOwner` without a field, or choosing someone, is the way. Only a role that may change everyone's records chooses whose a record is: anyone else makes their own, and the form leaves the field out for them. The operation `setOwner <model> [field]` sets it, and without a field returns the record to its creator |
| `capacity` | At most so many records per referenced record, e.g. a booking's places (see [Capacity](#capacity)) |
| `schedule` | Its records are people (or rooms, chairs) whose time is booked: weekly hours, breaks, a gap, time away (see [One person's time](#one-persons-time)) |
| `occupies` | Each record takes a scheduled record's time, e.g. an appointment its barber's (see [One person's time](#one-persons-time)) |
| `trash` | `true` keeps deleted records in a trash for thirty days (see [Trash](#trash)) |
| `review` | Holds the uploads of the fields it names until a reviewer approves them (see [Review](#review)) |
| `unique` | Fields unique together, e.g. `[[customer, number]]`: no two records hold the same values in all of them (see [Unique values](#unique-values)) |
| `thread` | What a conversation reads from the records when a page shows a list of them as a thread: `{ body: content, author: sender, side: { field: direction, ours: out } }`, each part optional; what is left out is read from the fields ([`record.lists`](#smithableuxyml-how-the-app-looks)) |

### Fields

Field names are camelCase (`email`, `creditLimit`); any word may be one, `default` and `new` too (an action's name may not be such a word, [actions](#actions)). A field is written in the **short form** or the **long form**.

**Short form:** `<type>[!] [unique] [= default]`

| Example | Meaning |
|---|---|
| `name: string` | Optional text |
| `name: string!` | Required text (`!` = required) |
| `email: email unique` | No two records may have the same email |
| `capacity: int! = 12` | Required whole number, default 12 |
| `status: draft \| sent \| paid` | One of these values. **The first value is the default** |

**Long form**, for anything more:

```yaml
level:
  type: beginner | allLevels | advanced
  default: allLevels            # a default other than the first value
rating:
  type: int
  required: true
  min: 1
  max: 5
  default: 3
  description: Stars from one to five.
priority:
  type: low | high
  default: none                 # stays empty until someone chooses
```

| Key | Meaning |
|---|---|
| `type` | A type, optionally with `!`, or choices (`a \| b \| c`) |
| `required` | `true` or `false` (same as `!`); or a condition, required while the record fits it: `required: { status: [inProgress, closed] }` |
| `by` | `app`: the form never shows the field; its value comes from its default, an action, an incoming entry, an import or code. For example `agent: { type: User, by: app, default: ME() }` |
| `sequence` | `true` on an `int!` with no default: each new record gets the next number, counting up from the records' highest in the same transaction, and a number given once is never given again, not after a delete nor after a restore from the trash (an order or invoice number); the field is unique, among an owner's records where unique fields are, else in the app. Numbers may skip (a refused create keeps its number); a backup restored puts the count back where the backup had it. The form never shows it, as with `by: app`. For example `number: { type: int!, sequence: true }` |
| `locked` | `true`: set when the record is made, never changed after; or a condition, read-only while the record fits it: `locked: { status: closed }`. The form shows it as fixed and the server refuses a change; an action's `set` may still change it, which is how a closed case is reopened |
| `unique` | `true` or `false`; or where the value is unique: `owner` (among one owner's records) or `app` (in the whole app). `true` is per owner when the model's records are read by their owners only, else in the app; see [Unique values](#unique-values) |
| `default` | A value of the field's type, or a [formula](#formulas) like `TODAY()`, or `ME()` on a field that refers to User: who makes the record. For choices, `none` means no default |
| `formula` | Makes the field computed: its value comes from a [formula](#formulas) and is not entered |
| `examples` | Inputs and expected results of the formula; each becomes a test |
| `min`, `max` | Bounds for `int`, `decimal` and `money`; for `string` and `text`, the length in characters (by default at most 200 for `string` and 10,000 for `text`) |

Plus the [semantic text](#semantic-text) keys.

A condition in `required` or `locked` is written as an action's `when`: a choice field's value or a list of them, a yes/no field's `true` or `false`, or a computed text or yes/no field's value (a computed one worked out as the record is loaded). A `locked` condition is read on the record as it is before the change, so an edit that both closes a case and changes a locked field is refused; a `required` condition on the record as it would be after it, when it is made or changed, so choosing the status that needs a field without giving the field is refused. `setFieldRules Order total --locked status=shipped` sets it (`--once` for `locked: true`, `--by app`, `--required status=placed`; an empty one removes it).

Changing a choice field's values (`changeField Order status "draft | placed | onItsWay | canceled" --renames shipped=onItsWay`) says what the records and samples holding a value that goes get instead (`shipped=` leaves them empty); a value still held that the change does not mention is refused, with how many hold it. A renamed value is followed wherever the app names it: in conditions (`where`, `when`, a field's `locked` and `required`), in what an action sets, in formulas that compare with it and their examples, in a long-form `default`, in what visitors may read, and in its tone and text. Where a value that is simply gone is named, the change is refused with the place. A choice field with a default always has a value, so it counts as required. A choice field with `default: none` is optional unless `required: true`.

### Relations

A field whose type is a model name refers to records of that model:

```yaml
models:
  Customer:
    fields:
      name: string!
      orders: Order[]          # every order that refers to this customer
  Order:
    fields:
      number: string! unique
      customer: Customer!      # each order belongs to exactly one customer
```

- **`customer: Customer!`** is a reference. Each order stores which customer it belongs to (in a `customerId` column); `!` makes it required, and `unique` allows each customer at most once. Forms show a list to choose from, and tables show the related record's name.
- **A record's title** is what the model's `namedBy` names, one part or several (a reference part is that record's own name, so names compose one step at a time); without it, by rule, its first short text field, else the first line of its first long text (sixty characters at most where it is shown), else its number. What a field is called plays no part: `smithable validate --explain` says which field the rule picked, and `namedBy` settles it.
- **`orders: Order[]`** is the other direction. It stores nothing: it lists the orders whose `customer` is this customer, and the customer's page shows them. The other model must have exactly one reference back, so it is always clear which records are listed. When the other model has a page of its own, the list has **Add <order>** for those who may create one: the new form opens with the reference to this record filled in and fixed, and goes back to it.
- A required reference prevents deleting the referenced record while it is in use (a customer with orders); an optional one is cleared instead.
- A model may refer to itself, e.g. `reportsTo: Employee`.

### Pictures

```yaml
models:
  Instructor:
    fields:
      name: string!
      portrait: picture
```

- A picture is chosen in the record's form. The browser scales it to at most 1600 px on the long side and encodes it as WebP before sending, so a phone's photo never travels whole; the server checks the file again (WebP by its header, at most 1 MB, its size read from the file) and stores it under `DATA_DIR/uploads/`, which `smithable backup` copies with the database. The record keeps `{ file, alt, width, height }`; the description (`alt`) is what those who cannot see the picture get, and lists show a thumbnail.
- A picture is shown at `/files/<model>/<id>/<field>`, loaded through the model's data function, so it can be seen exactly when its record can: a draft's cover is as private as the draft. Replacing or removing a picture removes its file when no other record shows it; deleting the record does the same. Whoever may add or change the model's records may send one; sending counts against the app's write limits.
- `pictures` holds up to ten pictures on one record, chosen in the form as a strip (add several at once, remove, reorder); the first is the cover that cards and tables show, and the record page shows them all, each opening large.
- A picture field cannot be `unique`, have a default, or appear in formulas, searches, dashboards or calendars. Sample data uses the starter's sample pictures (`public/images/samples/<n>.webp`) when it has any, one to three for a `pictures` field; a sample file gives several as a list.

### Documents

A `file` field holds one document on a record, as `picture` holds one picture: a contract on an invoice, a CV on an application, a receipt on an expense. `files` holds up to ten, in order.

```yaml
models:
  Invoice:
    fields:
      number: string! unique
      contract: file
      receipts: files
```

- A document is chosen in the record's form and sent as it is. The server reads its kind from the file's own first bytes, not its name: a PDF, an Office file (docx, xlsx, pptx), an OpenDocument file (odt, ods, odp), plain text, CSV, or a picture (PNG, JPEG, GIF, WebP), at most 10 MB; anything else is refused in the app's words. It is stored under `DATA_DIR/uploads/`, named by its content, so `smithable backup` copies it with the database. The record keeps `{ file, name, type, size }`.
- A document is served at `/files/<model>/<id>/<field>` (the n-th of several at `…/<field>/<n>`) through the model's data function, so it can be read exactly when its record can. It is sent with its stored type, never sniffed, and sandboxed: a PDF or a picture opens in the browser, anything else downloads. The record page shows each document's name and size as a link.
- Replacing or removing a document removes its file when no other record holds it; deleting the record does the same. Whoever may add or change the model's records may send one; sending counts against the app's write limits.
- A document field cannot be `unique`, have a default, or appear in formulas, searches, filters, sorts, dashboards or calendars. Sample data has no documents.

### Formulas

Computed fields and defaults use spreadsheet-style formulas:

```yaml
Order:
  fields:
    total: money!
    shippingMethod: standard | express
    shippingCost:
      type: money
      formula: IF(AND(shippingMethod = "standard", total > 100), 0, IF(shippingMethod = "express", 15, 5))
      examples:
        - input: { total: 150, shippingMethod: standard }
          expected: 0
Invoice:
  fields:
    issuedOn: date! = TODAY()
    dueOn:
      type: date!
      default: DATEADD(issuedOn, 30, "day")
    lines: InvoiceLine[]
    total:
      type: money
      formula: SUM(lines.amount)
```

- **Values:** numbers, text in double quotes (`"standard"`), `TRUE`/`FALSE`, and the fields of the same record by name. Money is in whole currency units (`100` is 100 EUR). Empty fields count as `0` or `""`, like blank cells.
- **Operators:** `+ - * /`, `&` joins text, comparisons `= <> < > <= >=`.
- **Functions:** `IF`, `AND`, `OR`, `NOT`, `ROUND`, `ABS`, `MIN`, `MAX`, `PMT(rate per period, periods, amount)` (a loan's payment per period), `TODAY`, `NOW` (the date and time, for date-and-time fields), `DATEADD(date, n, "day" | "month" | "year")`, `DAYS(end, start)`, `CONCAT`.
- **Over a list of related records:** `SUM(lines.amount)`, `AVG`, `MIN`, `MAX`, `COUNT(lines)`, `COUNTIF(bookings.status, "confirmed")`, and `LAST(messages.sender)` and `FIRST`: the value of the newest (oldest) record in the list by when it was made, empty for an empty list.
- A computed field is shown everywhere (forms show it read-only and update it as you type) but never entered. It cannot be required, unique or have a default.
- A formula default is filled in for new records, and can be changed.
- The operation `addField <model> <field> <type> --formula "<formula>"` adds a computed field (`addField InvoiceLine amount money --formula "quantity * unitPrice"`); in `addModel` and `addCalculatorPage` a field is the shorthand or, for a computed one, `{ "type": "money", "formula": "quantity * unitPrice" }`. A shorthand default that reads like a formula over other fields (`money = quantity * unitPrice`) is refused with that hint: `=` gives a default, set once.
- Formulas are checked when the spec is validated: unknown fields, wrong kinds of values, choice values that do not exist, and formulas that depend on themselves are reported. There are no user-defined functions or loops: anything beyond a spreadsheet cell is custom code.

## Unique values

A field's `unique` says no two records hold the same value, and where ([design/uniqueness.md](../design/uniqueness.md)):

```yaml
    fields:
      email: email unique                      # the short form: where, as the access says
      reference: { type: string, unique: owner } # among one owner's records
      code: { type: string, unique: app }        # in the whole app
    unique: [[customer, number]]                 # the two together, where as the access says
```

- **The short form** `unique` (or `unique: true`) is unique per owner when the model's records are read by their owners only (`private` access without a role that reads them all, and not public), else in the whole app: two members can both have invoice `2026-001` in a private app. `owner` and `app` say it outright, so a change of roles or public pages never moves the index. `owner` needs sign-in.
- **Fields unique together:** a model's `unique` lists sets of two or more stored fields; `{ fields: [customer, number], scope: app }` says where. A field unique by itself is not listed again.
- A number counting up (`sequence: true`) is unique by its nature, where its `unique` says, or as the access says when it has none.
- Changing where a value is unique, or adding a rule, is a change of the database's indexes, made by the next `smithable generate` like any schema change; records already breaking the new rule make that migration fail with the database's message, so check for duplicates first.
- The operations `setFieldRules <model> <field> --unique true|false|owner|app` and `setUnique <model> <field…> [--scope owner|app]` (`--remove` takes the rule away) set them. `smithable upgrade` writes the short form out once, as the access read it then (`unique: owner` or `app`), so the spec says what the database does; new specs may keep writing the short form.

## Trash

`trash: true` on a model keeps its deleted records in a trash for thirty days, where whoever may delete them can restore them or remove them for good; the rest of the app does not see them ([design/trash.md](../design/trash.md)). A unique value holds among the live records only, so a value a trashed record has can be used again, and restoring that record is then refused with the same words a new record gets; a record other records point to with a required reference goes to the trash together with them when their models have a trash too, after a dialog with the facts, and comes back with them; otherwise it cannot be trashed, and the refusal says what uses it ([design/delete-together.md](../design/delete-together.md)). The outgoing `deleted` event fires when the record is trashed. The operation `setTrash <Model> true|false` turns it on or off; off removes what is in the trash for good and asks first.

```yaml
models:
  Customer:
    trash: true
    fields: { name: string!, email: email }
```

## Review

`review` on a model holds the uploads of the picture, `pictures`, `file` and `files` fields it names (or `all` of them) until a reviewer approves them ([design/file-review.md](../design/file-review.md)). A reviewed field that is required holds the whole **record**: until its file is approved, the record is out of lists, search, dashboards, calendars, the API and the assistant's tools for everyone but its owner and the reviewers, and its owner sees it marked as awaiting review. An optional one holds only the **file**: the record shows as usual, and to others the picture is a blank awaiting review and the document is not offered. A new upload, and one replacing a file, starts waiting; a rejected one is removed and the reason is shown to the owner. A name that is no picture or file field is an error (`review-not-file`); `all` on a model without one is a warning (`review-nothing`), and so are files with no review page to wait on (`review-no-page`). Reviewers are the admins and the roles granted `review` in smithable.auth.yml; they are told by mail, each at most every fifteen minutes, how many files wait, and the review page's menu entry shows the number. Files a reviewer sends, sample data and files from before `review` was turned on are not held. The operation `setReview <Model> <fields…|all|none>` sets it.

```yaml
models:
  Listing:
    fields: { title: string!, photo: picture!, contract: file }
    review: [photo]                      # or all; photo is required, so a listing waits for it
```

## `pages`

Page names are camelCase or kebab-case (`customers`, `my-bookings`). Each page uses one pattern:

- **crud**: a list, detail view, and create/edit/delete for one model;
- **[landing](#landing-pages)**: a page for visitors, built from sections;
- **[dashboard](#dashboards)**: numbers, charts by month and the latest records;
- **[settings](#settings-and-onboarding)**: the form for the viewer's one record of a model;
- **[onboarding](#settings-and-onboarding)**: that record filled in steps, the first time someone signs in;
- **[users](#users)**: who has access: invite people by email with a role, change roles, remove users;
- **[data](#data)**: an administrator's view of the app's records, every model or some;
- **[calendar](#calendars)**: a model's records by week or month;
- **[articles](#articles)**: a model's records as articles: a blog, news or a knowledge base;
- **[calculator](#calculators)**: inputs and results computed as you type, stored nowhere;
- **[legal](#privacy-page)**: a privacy page written from the app itself;
- **[review](#review-1)**: the uploads waiting for a reviewer;
- **[custom](#pages-and-sections-of-your-own)**: a page of your own, written in code.

| Key | Required | Meaning |
|---|---|---|
| `crud`, [`landing`](#landing-pages), [`dashboard`](#dashboards), [`settings`](#settings-and-onboarding), [`onboarding`](#settings-and-onboarding), [`users`](#users), [`data`](#data), [`calendar`](#calendars), [`articles`](#articles), [`calculator`](#calculators), [`legal`](#privacy-page), [`review`](#review-1) or [`custom`](#pages-and-sections-of-your-own) | one of them | The pattern (see below) |
| [`sections`](#sections) | no | Parts of the page beside its kind's own, in order (a text, a FAQ, a model's records); alone, with no kind, a page of parts |
| `route` | no | Defaults to `/` plus the page name in kebab-case (`classTypes` → `/class-types`). `/health`, `/sign-in` and `/api/…` are reserved |
| `actions` | no | Crud pages: actions offered as buttons, e.g. `[mergeCustomers]` |
| `filters` | no | Crud pages: fields the list can be filtered by, e.g. `[category, price, available]`: a choice or a reference becomes chips (a select when there are more than eight values), a number, amount or date a range with "from" and "to", yes/no a toggle. Free text is searched, not filtered; pictures never; a field that refers to a person (`assignee: User`) gives chips for Mine, Unassigned and the people by name (a select when there are more than eight), in the address as `?assignee=me`, `none` or a person; `owner` gives signed-in viewers a "Mine" toggle. The state lives in the address (`?category=furniture&price=100..500`), so a filtered view can be linked; the query applies filters, search and sort together, within what the viewer may read. A date or date-time filter also takes a relative value, `upcoming` (from this moment; for a date without a time, from today), `past` (before that), `today`, `thisWeek` (from Monday) or `thisMonth`, resolved when the query runs in the app's time zone and kept in the address as written (`?startsAt=upcoming`). On phones the filters fold behind a "Filters" button; `smithable.ux.yml` may name the filters shown first on every screen |
| `defaultFilter` | no | Crud pages: filter values applied when the address says nothing, by filter, e.g. `{ startsAt: upcoming }` so a list of sessions opens on what is to come, or `{ status: [open, pending] }`; each must be among the page's `filters` and a value its filter takes (a date a relative value or a range, a number a range, a choice its values, yes/no `true` or `false`, `owner` `mine`, a person `me` or `none`; a reference to another record takes none). It shows as a chip the viewer can take away; the address then says `?startsAt=all`, which clears it. `setDefaultFilter sessions startsAt upcoming` sets one, `setDefaultFilter sessions startsAt none` removes it |
| `sortable` | no | Crud pages: fields the visitor may sort the list by, either way, from a "Sort by" control, e.g. `[price, createdAt]`; `smithable.ux.yml`'s `table.sort` stays the order until someone chooses. Not pictures, long text, lists of records or calculated fields (the query sorts by a stored column) |
| `mine` | no | Crud pages: `true` makes the page list only the viewer's own records (my items, my orders), with the same form to add one; it needs sign-in, so it never belongs under `public.pages`. The list's query keeps only the viewer's records, whatever the address says, and `filters: [owner]` gives no Mine toggle there |
| `favorites` | no | Crud pages: `true` gives each record a heart and the list a "Saved" view of the viewer's own marks (a visitor who clicks is asked to sign in; nothing is shown to others); `only` makes the page a list of the viewer's saved records. Each mark is the person's own (a table of its own, one row per person and record, gone with either); marking checks that the viewer may read the record. Needs sign-in: without it, nothing is generated |
| `contact` | no | Crud pages: a "Contact" block on the record page that mails the record's owner (`contact: owner`) or the user a field of the model names (`contact: seller`), with the record's title and link; the sender's address is the reply-to, the recipient's is never shown; nothing is stored unless `{ to: owner, keep: Message }` names a model of its own (no links to other records) to keep a copy in. Visitors may send on a public page, otherwise signed-in viewers (a signed-in sender's name and email are filled in and locked); limited like other writes; refused when the recipient cannot be reached |
| `search` | no | Crud pages: fields the list can be searched by, e.g. `[name, email]`: a search box finds records containing the text in any of them, ignoring case. Text, email, phone, web address and choice fields, and references (`[number, customer]` finds orders by their customer's name) |

Plus the [semantic text](#semantic-text) keys. Visible text such as titles does not belong here; it goes in [`smithable.content.yml`](#smithablecontentyml-visible-text).

### Sections

Any page is a list of named sections (docs/design/page-sections.md): its kind's own part first (a crud page's list, a dashboard's tiles, a calendar), and the `sections` written beside it. A page may also have `sections` alone, with no kind: a page of parts, in the app's frame unless the ux file says otherwise.

```yaml
pages:
  about:                                  # a page of parts, no kind
    sections:
      story: { text: }                    # a heading and paragraphs, from the content file
      team: { records: Instructor }       # a model's records as cards, as on a landing page
      faq:                                # a section named after its kind
      visit: { contact: }                 # a kind as an option gives the section any name
  sessions:
    crud: Session                         # the page's kind: its list and record pages
    sections:                             # more parts around it
      notice: { text: }
      crud:                               # where the page's own list sits (first, when not named)
      faq:
  planning:
    sections:
      week: { records: Session, view: calendar, starts: startsAt }   # a calendar on a page of parts
```

- The section kinds are the landing page's (`hero`, `features`, `records`, `pricing`, `testimonials`, `faq`, `callToAction`, `contact`, `gallery`, `footer`, `calculator`, `custom`) and `text`. A section is named after its kind, or has any name with the kind as an option written alone (`visit: { contact: }`), with `records: <Model>`, `text`, `calculator` or `custom`. A `records` section takes `view: cards | table | calendar` (cards by default) with `search`, `filters`, `where` and `limit` as on a landing page; a calendar view takes `starts`, the date field the records are placed by, needed when the model has more than one.
- Sections show in the order written. The page kind's own section comes first unless the kind's name stands among the sections, with nothing after it, to place it. A page's kind is written once, as its own key: `crud: Session` among the sections is refused, since a flow (a list with its record pages, an order's checkout) is a page, never a part of one. A landing page's sections stay under `landing`.
- Their texts are in `smithable.content.yml` under the page and the section's name, for every kind of page: `pages.sessions.notice: { title: Closed on Friday, text: … }`. A text section has a title and a text; the others as on a landing page.
- `addSection <page> <section> [--records Model] [--view table] [--starts field] [--text] [--custom Name]` adds one below the others, `removeSection` takes one and its texts away (never the page kind's own), `moveSection <page> <section> --before|--after <other>` moves one, the kind's own too once its name stands among the sections.
- The page's frame (the public frame with a top menu, the workspace with its side menu, or none) is `smithable.ux.yml`'s `pages.<id>.frame`.

### Landing pages

```yaml
pages:
  home:
    route: /
    landing:
      hero: { button: sessions, secondButton: pricing, shortcuts: [sessions, blog] }   # its buttons' pages; up to four shortcuts
      classes: { records: ClassType }     # a model's records as cards (limit: 6 by default)
      latest: { records: Item, search: true, filters: [category, price], limit: 8 }   # a catalog's door: the box and chips lead to the model's list page
      open: { records: Incident, where: { status: [investigating, identified] } }   # only the records these values fit
      features:
      pricing:
      testimonials:
      faq:
      callToAction: { button: sessions }
      gallery:                            # pictures that open large
      contact: { form: Message }          # details, and a form visitors send
      footer:                             # the page's own footer, wherever it is listed
```

- A records section may take `search: true` and `filters` (fields of its model, as on a crud page): the box and the chips lead to the model's list page with the same address state (`/?q=sofa`, `/?category=furniture`), so a front page can be a catalog's door without a second list. It offers what that list page reads: the box when the page has `search`, a chip row for each choice field among the page's `filters`. When the list page is public, each card opens its record. A crud page may take `route: /`, so the app starts on the list, in the site frame for visitors (with its records and its new form), and the landing page is optional.
- A records section may take `where`: it shows only the records whose choice fields have one of the values named (one value, or a list of them) and whose yes/no fields are `true` or `false`, as a dashboard tile does. A status page's front page shows the incidents not yet resolved; a shop's the featured products. The condition follows a renamed field and refuses to lose the field or a value it names. `addSection home open --records Incident --where "status=investigating | identified"` adds such a section, `setSectionWhere home open status=resolved` changes the condition and `setSectionWhere home open` clears it.
- Sections appear in the order written; `moveSection home faq --before features` (or `--after`) moves one. A section is named after its kind (`hero`, `features`, `pricing`, `testimonials`, `faq`, `callToAction`, `contact`, `gallery`, `footer`), or has any name and `records: <Model>`, `calculator: { fields: … }` (see [Calculators](#calculators)) or `custom: <Component>` (see [Pages and sections of your own](#pages-and-sections-of-your-own)).
- A hero's `shortcuts` are up to four pages, shown as round icons over its lower edge, each with its page's title and its navigation icon (`smithable.ux.yml`). The `setShortcuts` operation sets them.
- A hero's `button` is the page its button opens; without one, the page another section's button opens, else the app's first page (`validate --explain` says which). `secondButton` (a hero only) adds a second button beside it, an outline one, opening the page it names; a hero has none unless it is given. Its words are the content file's `secondButton`, the page's title when not given. `setHeroButtons home --button sessions --secondButton pricing` sets them, `none` takes one away; a removed page takes its button with it.
- A contact section shows an address (with a link to a map), phone, email and opening hours. With `form: <Model>` it also has that model's form: visitors add a record without an account, so the model must be listed under `public.create` in `smithable.auth.yml` (a warning says so) and cannot link to other records. A model of its own, like `Message` with a name, an email and a message, read only by admins, is the usual choice.
- Their texts are in `smithable.content.yml` under the page and the section's name. Without them, the hero shows the app's name and description, and records use the model's name. Features, pricing, testimonials and questions show nothing until the content file gives them items.
- A landing page has its own frame (the app's name and a way in), not the app's navigation, and is not in the default navigation. List it under `public.pages` in `smithable.auth.yml` to show it without sign-in; records cards show only what the visitor may read.

### Dashboards

```yaml
pages:
  overview:
    dashboard:
      outstanding: { sum: Invoice.total, where: { status: sent } }   # a number
      open: { count: Invoice, where: { status: sent } }
      average: { average: Invoice.total }
      invoiced: { sum: Invoice.total, by: issuedOn }                   # by month: a bar chart
      latest: { list: Invoice, limit: 5 }                              # the newest records
```

- Each tile is `count: <Model>`, `sum: <Model.field>`, `average: <Model.field>` (number or amount fields), `list: <Model>`, or `query: <query>` (a [query](#queries)'s records).
- `where` keeps records whose choice fields have a value (`status: sent`) or one of several (`status: [sent, overdue]`), or whose yes/no fields are `true` or `false`.
- `by` names a date field and turns a number into a bar chart of the last six months. `limit` is how many records a list shows (5 by default).
- The numbers are worked out from the records the viewer may read, so a dashboard follows the same access rules as the lists. Labels are in `smithable.content.yml`; by default they come from the tile names, which are camelCase like field names (`totalCost`, not `total-cost`).

### Settings and onboarding

```yaml
pages:
  settings:
    settings: BusinessProfile            # the viewer's business details
  welcome:

      model: BusinessProfile
      steps:                             # in order; each asks for some fields
        business: [businessName, vatNumber]
```

- An onboarding fills that record in steps, with Back, Continue and "Do this later". Signing in opens it (unless the visitor was on their way to another page), and once the record exists it hands over to the app's first page. The steps must ask for every required field without a default.
- Step titles and texts are in `smithable.content.yml`, under the page and the step's name (`business: { title: Your business, text: … }`); the heading is "Welcome to" the app, or the page's title. Onboarding pages have their own frame and are not in the default navigation.

### Users

```yaml
pages:
  team:
    users: manage                        # invite people, change roles, remove users
                                         # for administrators; a role gets it by naming it in its "pages" (smithable.auth.yml)
```

- The page lists everyone with access and the open invitations, with their role. From it, an administrator invites an email address with a role, changes a role, resends or withdraws an invitation, and removes a user. It is for admins unless a role's `pages` names it, needs sign-in, and an app has one.
- An invitation is a mail with a link to the sign-in page (also shown on the page, to send by hand). The invited person signs in with a configured provider using the invited address and has the invited role; the address decides, never the link. Invitations are valid for 14 days.
- Nobody can change their own role or remove themselves, and the last administrator stays one. Removing a user says which records name them (a reference to them, the records that are theirs, the trash included) and gives those to another member chosen in the dialog, in the same change; without one, what may be empty is cleared, and a required reference needs someone.
- With `selfSignUp: false` in `smithable.auth.yml`, only invited addresses and the `admins` can sign in at all.
- Everyone signed in sets the name others see from their name at the bottom of the menu; an invited person starts without one.
- Beside it, under its route and with its access, are the administrator's other pages: Trash (`/team/trash`, every model with a trash, each under its name, with Restore and Delete for good) and Activity (`/team/activity`). When the navigation shows the users page, the menu's last group, Admin, holds it with those two ([docs/design/admin.md](../design/admin.md)).

### Calendars

```yaml
pages:
  schedule:
    calendar: Session                    # short form: the model's one date or date-time field places records
    # calendar: { model: Session, starts: startsAt, duration: classType.durationMinutes, title: classType }
```

- A week view (days side by side, hours down the side, overlapping records side by side), a month view one button away, and on a phone a day-by-day list. Previous, Today and Next; the week or month is in the address (`/schedule?week=2026-W40`, `?month=2026-10`), so it can be shared.
- `starts` is the date or date-time field that places a record; it is inferred when the model has exactly one. `ends` (a field of the same kind) or `duration` (whole minutes: a field, or one reference away as `reference.field`) gives a record its length; without them a date-time record lasts an hour and a date one the day. `title` is what a block says (a field, or a reference's title); by default the model's title field, else its first required reference's title.
- Records are placed in the app's time zone (`app.timezone`), never the viewer's; without one the calendar warns and uses UTC. Forms read and write date-times in that zone too.
- Only the records whose start falls in the range shown are loaded, through the model's access rules, so visitors see what `public.read` allows. A record opens on its crud page (or a data page showing it) for those who may open that page; a visitor gets its details in a small panel. Those who may create records click an empty hour, and the new record's form starts then.
- The operation `addCalendarPage page model [starts]` adds one; "add a calendar for sessions" does too, without a model.

### Orders

```yaml
pages:
  menu:
    route: /
    order:
      from: Dish                               # what is chosen: one money field is its price
      into: Order                              # one record per order, with its one list of lines
      ask: [name, phone, wanted, note]         # the order's fields the customer fills, in order
      hours: { mon-thu: "11:00-20:00", fri-sat: "11:00-22:00" }
      lead: 20                                 # minutes from now to the earliest wanted time
```

- Visitors choose records of `from` with quantities and send them as one order: one `into` record and its lines in one write. The browser sends ids and quantities only; the server reads each chosen record, copies its price into the line, and refuses one that is not available (`available: bool` on `from`, when it has one) or that visitors may not read.
- `from` has one money field, its price, and may have one yes/no field, which says what can be ordered; with several, `price` and `available` name them (`available: none` for always). `into` has exactly one list, whose model has one reference to `from` and one money field for the price when ordered (the amount is a formula over it), a number counting up (`number: { type: int!, sequence: true }`), which the customer is told, and may have one whole-number field for how many (`quantity` names it when there are several, `quantity: none` for one of each). Nothing is read from a field's name ([inference](../design/inference.md)).
- `ask` names `into`'s own fields the customer fills: its plain values, so not a formula, the number, the list, a reference or a choice (a status is staff's). Without it, the required ones. A required field that is not asked and has no default is an error.
- `hours` says when orders are taken, in the app's time zone: a day (`mon` … `sun`) or a range (`mon-fri`) to a span `"11:00-20:00"` or a list of them; a day not named is closed. Without hours orders are always taken.
- The page is public when it is under `public.pages`; `into` must be under `public.create` and `from` under `public.read`, or a warning says so. It is not in the menu.
- The operation `addOrderPage page from into [--ask f,g] [--route /]` adds one. A renamed field in `ask` follows; a field the page relies on cannot be removed while the page is there.

### Calculators

```yaml
pages:
  mortgage:
    calculator:
      fields:
        price:   { type: money, min: 0, default: 300000 }
        deposit: { type: money, min: 0, default: 60000 }
        years:   { type: int, min: 5, max: 40, default: 25 }
        rate:    { type: decimal, min: 0, max: 20, default: 4.5 }
        monthly: { type: money, formula: "PMT(rate / 100 / 12, years * 12, price - deposit)" }
        total:   { type: money, formula: monthly * years * 12 }
      examples:
        - input: { price: 300000, deposit: 60000, years: 25, rate: 4.5 }
          expected: { monthly: 1334, total: 400200 }
```

- `fields` are written as a model's: the entered ones are the inputs, the formula fields the results, shown beside the inputs and computed as you type. No references, lists or pictures, nothing required or unique: nothing is stored, and an empty input counts as 0 or "". A formula inside `{ … }` goes in quotes, since its commas would otherwise split the line.
- `examples` become tests: each gives inputs and the results they must produce (several at once).
- A calculator page needs no sign-in by itself (list it under `public.pages` for visitors) and reads nothing. Its texts are keyed under the page: `pages.mortgage: { title: …, results: { title: Your payment }, fields: { rate: { label: Interest rate, help: The bank's yearly rate } } }`.
- On a landing page, a section of any name with `calculator: { fields: … }` is the same thing among the other sections; its texts are `title`, `text`, `results` (the results' heading) and `fields` under the section.
- The field operations (`addField`, `changeField`, `renameField`, `removeField`) take a calculator page's name where they take a model's; a rename follows into its formulas and examples. `renameModel <from> <to>` and `renamePage <from> <to>` rename a kind of record (its table and rows kept) or a page: every place the files name it follows, since the parser records where each name is written; a page without a `route` of its own moves to `/<new name>`. `addCalculatorPage mortgage price=money years=int` adds one; results are added with `addField … --formula` (see [Formulas](#formulas)).

### Articles

```yaml
pages:
  blog:
    articles: Post                       # short form: its parts are inferred
    # articles: { model: Post, title: title, body: body, picture: cover, date: publishedOn, address: address, summary: summary, author: author }
  posts: { crud: Post }                # where staff write them: a page the roles' grants name
```

- The short form reads each part from the fields' types, never from their names ([inference](../design/inference.md)): `title` is the record's title field, which must be a string (`namedBy` on the model settles it); `body` the model's one `markdown` field; `picture` its one `picture` field; `date` its one `date` or `datetime` field; `address` its one `unique` string besides the title; `summary` its one `text` field (the long form may name a string); `author` its one field that refers to a `User`. Only title and body are required. A part found twice is an error that names the long form, which settles it or leaves the part out with `none` (`author: none`).
- `/blog` lists the articles the viewer may read, newest first by the date (else by creation), 12 at a time, each with its picture, date and summary (the summary field, else the body's first paragraph). `/blog/<address>` shows one: its picture, title, date, the author's name when the articles have an `author` (named, or the model's one `User` field), the formatted body, links to the articles before and after it, and an Edit link for those who may change it on its crud page. Without an address field, articles are at `/blog/<id>`.
- On a public page (`public: pages` in `smithable.auth.yml`) the articles have the site's frame (the landing pages'), and each article's head carries its title, summary and picture for links shared elsewhere. Signed-in pages have the app's shell.
- Visitors read what the model's public read allows. With `- Post: { where: { status: published } }` a draft is neither listed nor found; `smithable validate` warns when a public articles page shows a model with a choice or yes/no field and no `where`.
- A new record's address, left empty, is made from its title (`Yin for beginners` → `yin-for-beginners`). A landing page's records section of the model links each card to its article.
- The operation `addArticlesPage page model` adds one; "add a blog for posts" and "add a news page for posts" do too, without a model.

## `actions`

An action is something the application does beyond create, edit and delete. A **custom** action declares what it takes and returns, and its behavior is code. A **standard** action sets fields of one record and needs no code (below).

An action's name is camelCase like a field's, and is refused when it is a word the code reserves (`return`, `delete`, `new`, …) or a model's name with a small first letter (`checkIn` beside a model `CheckIn`): the refusal names one that fits, the action's name with its model's (`returnTool`, `checkInHabit`).

```yaml
actions:
  mergeCustomers:
    custom: true
    input: { keep: Customer!, duplicate: Customer! }
    output: { moved: int! }                  # optional
    intent: Merge a duplicate customer record into the one we keep.
    rules:
      - All orders of the duplicate move to the kept customer.
```

- `input` and `output` use the field shorthand, including references (`Customer!` means choosing a customer). `unique` and defaults do not apply. One input may be a list of records, `customers: Customer[]` (always required, at most one, never of users): the action then runs on the rows picked in a list, its button in the selection bar, and its function gets the records the person may read; an output holds no list.
- Smithable generates the input schema, the input and output types and a server function, and creates `src/custom/actions/merge-customers.ts` **once**, with the intent and rules as a guide. That file is yours: Smithable never changes it. If the action's input or output changes in the spec, code that no longer fits fails type checking.
- A page lists actions to offer (`actions: [mergeCustomers]`); each gets a button and a form for its input.
- The action runs for the roles whose `actions` grant names it in `smithable.auth.yml` (admins always; see [Access](#access)). The implementation can ask who is signed in, and the generated data functions check access for that user.
- The operation `addAction <action> [name=type…] [--output name=type,…] [--intent "…"]` adds one, e.g. `smithable op addAction mergeCustomers keep=Customer! duplicate=Customer!`. Builder's form is "An action", and "add an action to merge customers" needs no model.

### Standard actions

A standard action is a button that moves a record to its next state: resolve an incident, mark an invoice paid, cancel a booking. It names the model, when it applies, and the new values. [Buttons that change a record](https://docs.smithable.ai/actions.html) walks through each kind on the invoicing starter.

```yaml
actions:
  resolve:
    on: Incident                                              # the record it changes
    when: { status: [investigating, identified, monitoring] }  # optional: offered and allowed only then
    set: { status: resolved, resolvedAt: NOW() }              # the new values
  markPaid:
    on: Invoice
    when: { status: sent }
    set: { status: paid, paidOn: TODAY() }
```

- `on` names a model; the action runs on one record of it.
- `set` gives fields of that model their new values (or `add` creates a related record; an action has `set`, `add` or both). A value with parentheses is a formula from the formula library, worked out on the record as it was before the change (`NOW()`, `DATEADD(TODAY(), 14, "day")`, `(total * 0.25)`); anything else is a literal the field accepts (a choice value, `true`, a number, a text), as for defaults. Computed fields, references, lists and pictures cannot be set; a field without a value is asked for (below).
- **Asking for a value:** a key in `set` with no value (`cancelReason:`) is asked for when the button is pressed. A dialog titled with the action holds the asked fields with their own controls, starting at the record's values and required as on the model. Several may be asked at once.
- **Adding a related record:** `add` maps a model that refers to this one exactly once to the values of one new record, created in the same transaction as `set`. The reference back is filled with the record and is not given; values work as in `set` (a literal, a formula on this record, or nothing to ask for it), and every required field without a default needs one. Running the action then also needs the right to create that model's records.

  ```yaml
  resolve:
    on: Incident
    when: { status: [investigating, identified, monitoring] }
    set: { status: resolved, resolvedAt: NOW() }
    add:
      IncidentUpdate: { at: NOW(), status: resolved, message: This incident is resolved. }
  ```
- **Copying:** `copy` makes a new record of the model from the one the action runs on, instead of changing it: every stored field and reference is copied except computed fields, the automatic ones (the copy is owned by whoever pressed the button), pictures and unique fields; the map says what differs, with values as in `set` (`copy: {}` copies as is). `with: [lines]` copies the records of those lists too, pointing at the new record; a list's records the person may not read are not copied. A required unique field must get a formula or be asked for; a model with a required picture cannot be copied yet. The person lands on the copy. An action has `copy`, or `set` and `add`, never both; it needs the right to read the record and to create such records (and the lists' records).

  ```yaml
  duplicate:
    on: Invoice
    copy: { status: draft, issuedOn: TODAY(), number: }
    with: [lines]
  ```
- **The person pressing the button:** `ME()` as a whole value, in `set`, `add` or `copy`, puts in the signed-in person, for a field that refers to `User` (`set: { assignee: ME() }`). A reference left empty (`set: { assignee: }`) is asked for in the dialog, with the form's own control for it; a literal reference is refused.
- `when` is a condition like the others: a choice field's value or a list of them, a yes/no field's `true` or `false`; a computed text or yes/no field may be named too (`lastSender: agent`, with `lastSender: { type: string, formula: LAST(messages.sender) }`), read on the record as it is loaded, so never in `where`, filters or sort. Such a condition is text: a renamed choice value is not followed in it. A reference field may be named too, only here: `none` (empty), `any` (set), and for a field that refers to `User` `ME()` (the record is the signed-in person's) or `not ME()` (anyone's but theirs, or nobody's), so "Assign to me" shows only on cases that are not already yours (`when: { assignee: not ME() }`) and "Release" only on yours. The button shows only on records it fits, and the server refuses the action on others ("This cannot be done now").
- No `input`, `output` or `custom`: an action is custom or standard. `rules` are documentation only, and a warning says so.
- **Access:** a standard action follows its model's write access: whoever may change the record may run it, which is each one for their own records and the roles granted `write` on the model in `smithable.auth.yml` (admins always); and a role whose `actions` grant names it runs it too, without `write` on the model (`grant customer actions cancel`: a customer cancels their own booking but changes nothing else), as a role opens the pages its `pages` grant names; `actions: all` is every action. An action that adds a related record also needs the right to create one. The action writes only the fields its `set` names and the ones it asks for, and may change a `locked` field only when `set` names it; a copy follows the right to create.
- A page lists it as any action (`actions: [resolve]`), and it must be a crud page of the action's model.
- Renaming a field renames it in `when`, `set` and the formulas there. Removing a field the action uses, or a choice value it wants or sets, is refused until the action changes.
- The operation `addAction <action> --on <Model> [--when field=value…] [--set field=value…] [--add Model.field=value…] [--copy field=value…] [--with list…]` adds one (an empty value asks for the field; a bare `--copy` copies as is), and puts it on the model's crud page when the model has exactly one, e.g. `smithable op addAction resolve --on Incident --when "status=investigating | identified" --set status=resolved --set "resolvedAt=NOW()"`.
- The operation `setAction <action> [--intent "…"] [--when field=value…] [--set field=value…]` changes an action there is: each part named replaces what was there (a bare `--when` or `--intent ""` removes it), and the rest stays; `--when` and `--set` are for standard actions, the intent for any. `removeAction <action>` removes one, from the pages that list it and from `api.actions` in `smithable.auth.yml`; a custom action's code in `src/custom/actions/` stays. Who may run an action is `grant <role> actions <name>` in `smithable.auth.yml` ([Access](#access)).

## `timers`

What the app does on a clock ([design/timed-actions.md](../design/timed-actions.md)): a timer is an event the app raises itself at a time, on a schedule or relative to a date-time of a record, and may run an action over the records the time has come for. Mail and calls stay `outgoing`'s, whose `when` names a timer as it names an action. The spec holds the timer because what the app does on a clock is what the app does: versioned, generated, shown in What it does, undoable.

```yaml
timers:
  remind:
    on: Booking                             # the records it runs for
    at: 1 day before session.startsAt       # a date-time of the record, or one reference away, with an offset
    where: { status: confirmed }            # optional: only records that fit
                                            # no run: the timer only raises its event; outgoing listens
  markOverdue:
    on: Invoice
    at: 7 days after dueOn
    where: { status: sent }
    run: markOverdue                        # a standard action of Invoice; a record its when does not fit is skipped
  publish:
    on: Post
    at: publishAt                           # as it is: when the time comes
    run: publish
  weeklyDigest:
    every: monday                           # day | weekday | week | month | monday … sunday
    at: "08:00"                             # a clock time, in the app's time zone
    run: sendDigest                         # a custom action, once
  payroll:
    cron: "0 6 25 * *"                      # what every cannot say: five fields, the app's time zone
    run: closePayroll

outgoing:
  reminder:
    when: remind                            # a timer's name, as an action's
    to: mail
    recipient: owner
```

- A timer has one of three forms. **At a date of its records**: `on` and `at: <field> [N minutes|hours|days before|after]`, the field a stored date or date-time of the model or one reference away (`session.startsAt`); it fires once per record for that time, follows a moved time, and leaves alone a record whose time had passed when the timer was added. **On a clock**: `every` (`day`, `weekday`, `week`, `month`, which fire on the first day of theirs, or a weekday's name) with `at`, a clock time in the app's time zone. **By cron**: the five-field expression (minute, hour, day of the month, month, weekday; `*`, numbers, ranges, steps and lists; no names, which are `every`'s), for what `every` cannot say.
- `run` is a standard action of `on` (run for each record the timer is due for; one its `when` does not fit is skipped and Activity says so) or a custom action (run once, so the timer has no `on`). A timer without `run` only raises its event, which is how a reminder with no state change is written: the timer and an outgoing entry on it. A clock timer with `on` runs its action over every record fitting `where`, and its event fires once per record. A timer with neither `on` nor `run` is refused.
- A timer runs as the app, with no viewer: no role's grants apply, as for incoming calls. Delivery is never the timer's: a channel is `outgoing`'s `to`.
- The summary says each timer in one sentence ("A day before a booking's session's starts at, where status is confirmed: raises its event"; "Every Monday at 08:00: runs “Send digest”"; "At 06:00 on the 25th of every month: runs “Close payroll”").
- A timer follows a renamed field in its `at` and `where`, and refuses the removal of a field or an action it uses; `removeTimer` refuses while an outgoing entry listens to the timer.
- Operations: `addTimer <name> [--on Model] [--at "1 day before session.startsAt" | --every day --at 08:00 | --cron "0 6 * * *"] [--where field=value…] [--run action]`, `setTimer <name> …` (a new time form replaces the old; `none` takes `where`, `run` or `on` away) and `removeTimer <name>`.
- The generated app's tick, `smithable timers` and Studio's picker follow the core (timed-actions.md §5, §7).

## `outgoing`

Something happens to a record and the app tells someone. An entry names what happens, whom to tell and how. Mail is built in; a signed call to a named target comes next ([design/integrations.md §4](../design/integrations.md)).

```yaml
outgoing:
  bookingMade:
    when: Booking created            # <Model> created | changed | deleted, or an action's name
    to: mail
    recipient: owner                 # the record's owner; a role (admin); or an address on the record
  bookingConfirmed:
    when: Booking changed
    where: { status: confirmed }     # optional: only records that fit
    to: mail
    recipient: customer.email        # an email field, or a field that refers to User, one reference away at most
    show: [number, wanted, total]    # optional: the fields the mail lists under its text (a call's record carries), in this order; none for the text alone
    previous: true                   # optional, for "<Model> changed": what the changed fields were, too
  sessionMoved:
    when: Session changed
    fields: [startsAt]               # optional: only a change of these fields counts
    to: mail
    recipient: bookings.owner        # a list field, then the owner or an address of each of its records
```

- `when` is `<Model> created`, `<Model> changed` or `<Model> deleted`, the name of a standard action (the model is the action's `on`), the name of a custom action (fired after its function returns without an error; there is no record, so a call's body carries the action's `input` and `output`, a mail shows them, a mail goes to a role, and `where` and `fields` are refused), or the name of a [timer](#timers) that has `on` (the model is the timer's; its event comes per record the timer is due for). A name that is both an action's and a timer's is refused, since `when` cannot tell them apart. With `where`, a creation or deletion counts when the record fits it, and a change counts when the record fits it after the change and did not before, so an edit to a record that already fits sends nothing. Without `where`, every change counts. A `<Model> changed` entry may name `fields`: then only a change of one of those stored fields counts (a session's `startsAt`, not its description), with `where` as well when both are given.
- `recipient`, for mail, is `owner` (the record's owner; a record without an owner sends nothing), a role from `smithable.auth.yml` (every user who has it), an `email` field of the record or a field that refers to User, or either of those one reference away (`customer.email`, `customer.manager`); or a list field of the record and then `owner` or such an address of each of its records (`bookings.owner`, `bookings.contact`): every booking's owner is told when the session changes, each person once, none for a record in the trash. One recipient per entry. The person whose change it is gets no mail about their own change or deletion; a confirmation of what they created (`<Model> created`) is theirs, as a booking's is.
- The mail's subject is the record's title unless `smithable.content.yml` gives one under `outgoing: { bookingMade: { subject, text } }`; the body is that text, if any, then the record's fields as the record page shows them (labels and formatted values, references by their titles; nothing a files or pictures field holds, nothing sensitive, no lists of other records, no worked-out fields), and a link to the record ([design/outgoing-templates.md](../design/outgoing-templates.md)).
- The subject and the text may hold placeholders in the `{path}` form the spec has elsewhere, filled from the record as its page shows the value: `{number}` a field of the record; `{customer}` a reference's record by its title and `{customer.name}` a field of that record, one hop; `{title}` the record's title, `{link}` its page's address, `{by}` the name of the person whose change it is (empty for a timer's or an incoming call's event); `{before.status}` what a field was, on `<Model> changed` only. An empty value is an empty text; there are no conditions, fallbacks or formatting codes, and no way to write a literal brace (a text with braces is a template since this change). `title`, `link`, `by` and `before` are the mail's own words: a field with one of those names is not reached by a placeholder. A path that is not a field, holds files, looks sensitive, lists records, is worked out, or goes two hops is refused when the content file is checked; so is a reference's field the recipient may not read (its title is fine; another field needs a role recipient who may read that model), and `{by}` to an address on the record is a warning. A custom action's entry takes no placeholders.
- `show` names the fields the mail lists under its text and a call's record carries, in that order, each one the record page could show (no files, nothing sensitive, no lists, no worked-out fields), or is `none` for the text alone (a call's record then has its id only). `previous: true`, on `<Model> changed`, adds what the changed fields among the sent ones were: the mail's line reads "Status: ready (was accepted)" and a call's body gets `before` with those fields. A role recipient who may not read the model is a warning for the default body and an error when the entry has `show` or a text with placeholders.
- The mail is written to an outbox in the same transaction as the change and sent after it, so a change never waits for the mail; one that cannot be sent is tried again with growing pauses for a day, then given up. Activity has a line for each mail sent or given up, and an administrator can send a given-up mail again from it.
- `to` is `mail`, or the camelCase name of a target whose address and secret are settings (`OUTGOING_<TARGET>_URL`, `OUTGOING_<TARGET>_SECRET`, e.g. `OUTGOING_STATUSFEED_URL`); a target takes no `recipient`. A call is a POST of `{ event, model, happened, at, record }`, the record as the API gives it (without computed values or what looks sensitive), with `X-Event: <entry>` and `X-Signature-256: sha256=<the HMAC-SHA256 of the body with the secret>`, so the receiver can check it came from the app; it should also refuse a call whose `at` is more than a few minutes old, so a call caught on the way cannot be sent again later. It goes through an outbox like the mail, retried for a day; a target without its settings keeps its calls until they are set, and `smithable deploy` names the missing settings. The app refuses an address that is not http(s), is the app itself, or (in a release) is on a private or local network; it does not follow redirects. Activity has a line per call made or given up, with "Send again".
- An entry follows a renamed field or choice value and refuses the removal of a field, a value or an action it uses. `smithable validate` warns when a mail's recipient is an email field on a model visitors may create (the app does not send those: a stranger could make it mail anyone) and when a role recipient may not read the model (the mail would tell them what the record holds).
- Operations: `addOutgoing <name> <when> [--where field=value…] [--fields field…] [--show field…|none] [--previous true] [--to mail|<target>] [--recipient …]`, `setOutgoingBody <name> [--show field…|none|default] [--previous true|false]` and `removeOutgoing <name>`, e.g. `smithable op addOutgoing bookingMade "Booking created" --recipient owner` or `addOutgoing sessionMoved "Session changed" --fields startsAt --recipient bookings.owner`. The summary line reads "When a booking is added: mails its owner." or "When a session's starts at changes: mails every booking's owner."

## `incoming`

Another service calls the app: a monitor that finds a site down, a form service, a payment provider. An entry names an address of the app, `/incoming/<name>`, and what a call does ([design/integrations.md §3](../design/integrations.md)).

```yaml
incoming:
  monitorDown:
    create: Incident                 # one record per call
    set:
      title: "{check.name} is not responding"   # {path}: a value from the call's JSON
      status: investigating
      detectedAt: NOW()
    id: "{event.id}"                 # optional: a call seen in the last day is not acted on again
    as: staff                        # the role the call acts as (admin when not said)
  paymentReceived:
    custom: true                     # src/custom/incoming/payment-received.ts decides
    signed: sha256                   # a signature of the body, not the secret itself
  chatCommand:                       # a chat tool's slash command opens an incident
    create: Incident
    set: { title: "{text}", status: investigating, detectedAt: NOW() }
    body: form                       # the command comes form-encoded, not as JSON
    signed: { sha256: "v0:{timestamp}:{body}", prefix: "v0=", timestamp: X-Slack-Request-Timestamp }
    header: X-Slack-Signature
    challenge: challenge             # the tool's setup check: answered with the value, nothing else
    as: staff
```

- `create` with `set` adds one record per call. A value is a literal the field accepts, a formula (`NOW()`), or a text with `{path}` placeholders filled from the call's JSON body (`{check.name}`, `{items.0.id}`); a missing path is an empty text, and a required field left empty refuses the call. References, lists and files are not set by a call yet.
- `custom: true` hands the verified call to `src/custom/incoming/<name>.ts`, created once as a stub that answers "received"; it uses the generated data functions, so the access rules hold. For what a template cannot say: find a record and change it, several records, another answer.
- The secret is a setting, `INCOMING_<NAME>_SECRET` (e.g. `INCOMING_MONITORDOWN_SECRET`): the caller sends it as `Authorization: Bearer <secret>`; with `signed: sha256` it sends `sha256=<hex>` of an HMAC of the body instead, in `X-Signature-256` unless `header` names another. Without the setting the address refuses every call.
- `signed` may be a map for a service's own form of the same signature: `sha256` is what is signed, a text of `{body}` and, when the service signs the call's time too, `{timestamp}` (`"v0:{timestamp}:{body}"`); `prefix` what comes before the hex (`sha256=` unless said; `v0=`); `timestamp` the header the time comes in, seconds since 1970 (or milliseconds). A call whose time is more than five minutes off is refused, and within those minutes a call with the same signature is a repeat (answered as received, not acted on again), so a captured call cannot be sent again. The text must take `{body}`, and `{timestamp}` and `timestamp` go together. `signed: sha256` is `{ sha256: "{body}", prefix: "sha256=" }`.
- `body: form`: the call's body is form-encoded (`key=value&…`, as slash commands and interactive messages come) rather than JSON; `{path}` reads its fields, and a field whose value is JSON (`payload`) is read as JSON, so `{payload.user.name}` reaches into it. A call that says it is JSON (its `Content-Type`) is read as JSON all the same, so one address takes a service's commands and its events. Not for a mail.
- `challenge: <path>`: a call whose body has a value at that path is the service's setup check of the address: the app answers `200` with the value as plain text and does nothing else, whatever else the call carries. The call is verified first, like any other. Not for a mail.
- `as` is a role from `smithable.auth.yml`; the record goes through that role's create rule and has no owner, as a key's. `smithable validate` warns when the role may not create the model. Without `as` the call acts as `admin`, and the summary says so. For a `custom: true` entry, whose code may do anything that role may, a lower role is the safer choice.
- A call carrying an id seen in the last day (the `Idempotency-Key` header, or the value `id` names) is answered as received and not acted on again: services retry.
- Answers: `201` with the new record's id, `200` for a repeat or a custom call, `401` for a wrong secret or signature, `422` when the record is refused (a required field empty, a value the field does not take).
- `mail: true` makes each call a mail that becomes a record: the body is the mail a host passes on, `{ from, to, subject, text, html, attachments: [{ name, type, data }] }` (data in base64), and `fields` names where its parts go: `from` to an email or text field (the address alone, out of "Name <address>"), `subject` to a text field, `body` to a text or Markdown field (the text, or the HTML without its tags), `attachments` to a `files` or `file` field. Attachments are kept as uploads are: at most 10 MB each, checked, and held for review when the model reviews that field. `set` gives the rest (`status: new`). Who passes the mail on is the host's: on smithable.ai a mailbox the owner connects, self-hosted the owner's own receiver.

```yaml
incoming:
  support:
    mail: true
    create: Request
    set: { status: new }
    fields: { from: email, subject: title, body: body, attachments: files }
    reply:                           # a mail of one of its requests' threads
      create: Message                # refers to Request once (Message.request)
      fields: { from: from, body: body, attachments: files }
      set: { direction: in }
      then: { status: open }         # on the request it joins: a reply reopens it
```

- `reply` makes a mail that belongs to the thread of a record the entry made into one record of `reply.create`, referring to that record, instead of a new one. That model must refer to the entry's `create` exactly once; the engine fills the reference. `fields` and `set` work as the entry's own; `then` sets fields of the record the reply joins. A mail finds its thread by its `In-Reply-To` and `References` headers first, among the message ids the app sent or received about the record (kept in the kit's `mail_threads` table), else by a tag `[<app> #<id>]` in its subject; neither is a new record. An automatic reply (`Auto-Submitted`, a bulk or list `Precedence`, a delivery report) joins its thread but sends nothing back. A host passes `messageId`, `inReplyTo`, `references` (an array) and `autoSubmitted` beside the mail; without them the tag still works.
- Every mail the app sends about such a record or its replies is a thread mail: its subject ends with the tag (`Printer out of toner [Harbour Support #12]`), it carries `In-Reply-To` and `References` of the thread and `Reply-To` the mailbox the entry is fed from (the setting `INCOMING_<NAME>_ADDRESS`, else `MAIL_FROM`), and a mail about a reply is the reply's body alone, a letter rather than a record with labels. Every mail the app sends is marked `Auto-Submitted: auto-generated`, so auto-responders do not answer it and a mailbox watcher does not take it back in (on smithable.ai the relay also marks it as the app's).
- Operations: `addIncoming <name> --create <Model> --set field=value… [--signed | --signed-text "v0:{timestamp}:{body}" --signed-prefix v0= --timestamp <Header>] [--header <Header>] [--form] [--challenge <path>] [--as <role>]`, `addIncoming <name> --custom`, `addIncoming <name> --mail --create <Model> --fields from=email subject=title body=body attachments=files [--reply Message --reply-fields from=from body=body [--reply-set direction=in] [--reply-then status=open]]`, `setIncomingReply <name> --create Message --fields … [--set …] [--then …]` or `setIncomingReply <name> --none`, `removeIncoming <name>`. A renamed field follows into the entry; removing one it names is refused.

## `queries`

A query is records chosen or ordered by code, for what a filter cannot say:

```yaml
queries:
  churnRisk:
    custom: true
    returns: Customer[]
    intent: Customers most likely to stop buying, most at risk first.
    rules:
      - A customer without an order in 90 days is at risk.
```

- Smithable generates the result's type (`src/generated/queries/churn-risk.ts`) and creates `src/custom/queries/churn-risk.ts` **once**, as a stub that returns every record the viewer may read. That file is yours; its code starts from the data functions, which apply the access rules.
- A dashboard shows a query's records with `atRisk: { query: churnRisk, limit: 5 }`.
- `smithable code query:churnRisk "<what to do>"` has a model write the code (see [docs/ai.md](../ai.md)); only files in `src/custom/` may change, and the type check and tests must pass.

## Sections Smithable does not know: project plugins

A top-level key that no built-in section or plugin handles is an error, never ignored. `smithable teach <key>` has a model write a **project plugin** for it once: `smithable/plugins/<key>/plugin.mjs`, declared in `smithable.context.yml` (`plugins: [newsletter]`). After that, the section is handled without AI:

```yaml
newsletter:                      # handled by smithable/plugins/newsletter/plugin.mjs
  from: hello@stillwater.ax
  lists: [classes, offers]
```

A plugin is one ES module without imports, exporting `{ key, description, schema, expand?, patch?, generate?, operations?, summarize? }`, or a function of the plugin API (`OperationError`, `didYouMean`, `identifier`, `kebab`, `refTo`) returning it:

- `schema`: the JSON Schema of the section (type, properties, required, additionalProperties, items, enum, pattern, minItems and uniqueItems are checked).
- `expand(value)`: the ordinary spec the section stands for (`models`, `pages`, `queries`, `actions`), merged in as if written by hand, so the database, pages, forms and access checks are built as usual. Clashes with names in `smithable.yml` are errors, reported at the plugin's section.
- `patch(value)`: additions to entries `smithable.yml` already has, never changes or removals: `{ add: "field", model, field, type }`, `{ add: "section", page, section, value? }` on a landing page, `{ add: "menu", page, menu?, position? }`. A missing target or a clash is an error at the plugin's section.
- `operations`: operations on the section, shaped like Smithable's own (`name`, `summary`, `schema`, `positional`, `describe`, `destructive`, `apply(editors, args, ir)`); they appear in `smithable op`, the MCP tools, Studio and what the AI may propose. A name a built-in operation has is offered as `<key>:<name>`.
- `summarize(value)`: the section in plain language for the Builder, one sentence per item.
- `generate(value, ir)`: optional extra files, only under `src/generated/plugins/<key>/`, the same for the same input.

## Capacity

```yaml
models:
  Session:
    fields: { startsAt: datetime!, capacity: int! = 12, bookings: Booking[] }
  Booking:
    fields:
      session: Session! unique           # with private access: one booking per member and session
      status: confirmed | canceled
    capacity:
      per: session
      max: session.capacity
      where: { status: confirmed }
      closes: 2 hours before session.startsAt     # optional: booking until then (the start itself, written as the field)
      cancelUntil: 24 hours before session.startsAt   # optional: the owner cancels until then; staff always may
```

- `per` is one of the model's required references; `max` a whole number, or a whole-number field of the referenced record written as `reference.field`; `where` (optional) counts only records with these choice values (one, or a list of them) or yes/no values.
- The check happens where the record is saved, in the same transaction as the write: two people taking the last place at once cannot both get it. A record over the limit is refused ("No places left"); lowering the referenced record's number below what is taken is refused too ("3 are already taken").
- One booking per person is the field's `unique`, which under private access means unique per owner. `smithable validate` warns when `per` is not unique ("one person can take several places"), which is sometimes intended (tickets). It warns too when `per` is unique and the records are not private: then `unique` holds across the app, one booking per session in all, and a `max` above 1 is never reached.
- `closes` and `cancelUntil` (optional) are deadlines: a date-time field of the referenced record, written as `reference.field` (until that time) or as a period before it, `<number> <minutes|hours|days> before reference.field`. Past `closes`, a new record is refused on every path (the form, Book a place, the API, the assistant) with "Booking has closed."; past `cancelUntil`, its owner's deletion is refused with "Cancelling has closed.". A role that may change (for `closes`) or delete (for `cancelUntil`) everyone's records passes, and Activity has the line as for any change. Nothing is stored: the deadline is read from the referenced record when a write is checked, so a moved session moves its deadlines. The places (below) say `closesAt` and `cancelUntilAt` for the block's words.
- The operation `setCapacity <model> <per> <max> [key=value…] [--closes …] [--cancelUntil …]` sets it (`none` lifts a deadline); `setCapacity <model> none` removes it.
- **Book and Cancel.** With sign-in, the referenced record's page (and its panel in a calendar) shows its places ("3 of 12 places left", "Full") and a reservation block. A visitor gets "Sign in to book", which comes back to the page. A signed-in person who may create the model gets **Book a place**, which creates the record in one step (its other fields take their defaults). After that the block says "You're booked", with **Cancel booking**, which asks first and deletes the record through its data function. The places are counted over every record, and only the numbers leave the server.
- Records with a capacity get no sample data: every place starts free.

## One person's time

```yaml
models:
  Service:
    fields: { name: string!, minutes: int!, price: money }
  Barber:
    fields: { name: string!, phone: phone }
    schedule:
      hours: { mon-fri: "09:00-17:00", sat: "10:00-14:00" }
      breaks: "12:00-12:30"
      gap: 10                          # minutes kept free after each appointment
      away: TimeOff                    # records of days or hours away
  TimeOff:
    fields: { barber: Barber!, from: datetime!, until: datetime!, note: string }
  Appointment:
    fields:
      service: Service!
      barber: Barber!
      startsAt: datetime!
      status: requested | confirmed | cancelled
    occupies:
      resource: barber
      starts: startsAt
      duration: service.minutes
      while: { status: [requested, confirmed] }
      cancelUntil: 12h
```

A class takes places on a session ([Capacity](#capacity)); a barber, a physiotherapist or a court is booked by **its time**: one appointment at a time, inside its hours.

- **`schedule`** says a model's records are booked by their time. `hours` are the business's week in the app's time zone (`app.timezone`), as an order page's: a weekday or a range of them (`mon-fri`, `fri-sun`) to a span (`"09:00-17:00"`) or a list of spans; a day not named is closed. `breaks` (a span or a list) are kept free every open day; `gap` is the minutes kept free after each booking. `away` names a model whose records block time (days off, holidays, an afternoon at the dentist): its name alone takes its one reference to this model and its first two date-and-time fields, in the order it writes them, as when the time away starts and ends; `away: { model: TimeOff, resource: barber, from: from, until: until }` says them. The summary names the fields it reads.
- **`occupies`** says each record takes `resource`'s time (one of the model's required references, to a model with a `schedule`) from `starts` (a date-and-time field) for `duration` minutes (a whole-number field, of the record or of one it refers to, as a calendar's `duration`), while `while` holds (choice values, or yes/no, as a capacity's `where`; without it, always). One `occupies` per model.
- **Cancel.** It needs `while` to name one choice field, the one it sets. With `cancelUntil` (a whole number and a unit: `30m`, `12h`, `2d`) the record's owner gets **Cancel** until that long before its start; after that the button says to contact the business, and roles with write on the model may still change it. It sets the one choice field of `while` to the value outside it (`cancelled` here); when several values are outside it, `cancelTo` names the one. `cancelTo` alone gives the Cancel until the start.
- **Never two at once.** The check happens where the record is saved, in the same transaction as the write: a time outside the hours, in a break, while away, or overlapping another record of the same resource (with the gap after it) is refused, with the next free times. Two people taking the same time at once cannot both get it.
- Records that occupy someone's time, and the records of time away, get no sample data: every free time starts free.
- The operations: `setSchedule <model> <hours> [--breaks …] [--gap …] [--away <model>]` (hours as `"mon-fri 09:00-17:00, sat 10:00-14:00"`; `none` removes it, refused while a model occupies it) and `setOccupies <model> <resource> <starts> <duration> [key=value…] [--cancel-until …] [--cancel-to …]` (`none` as the resource removes it).

## Access

Who may do what is said in [`smithable.auth.yml`](#smithableauthyml-sign-in-roles-and-what-is-public), in full; `smithable.yml` names no role ([design/access-in-auth.md](../design/access-in-auth.md)). Three rules, and nothing implied beyond them:

1. **The record rule** is `defaultAccess`: with `shared` everyone who signs in reads every record, with `private` only their own. Everyone changes and deletes their own records.
2. **A role does what its block grants**, shaped like `public`: the pages it opens, the models it adds records to (`create`), reads everyone's records of (`read`, with `private`), changes (`write`) or deletes (`delete`) everyone's records of, and the custom actions it runs (`actions`). Each is a list of names, or `all`. A role with no block has the record rule and nothing more; `smithable validate` warns when a role can open no page.
3. **Administrators do everything**: `admin: all`, written in the file; anything else under `admin` is an error.

| | `shared` (internal tools, teams) | `private` (SaaS, consumer apps) |
|---|---|---|
| Read | Everyone who signs in | The owner, and roles granted `read` |
| Create | Roles granted `create` | Roles granted `create` |
| Change and delete | The owner, and roles granted `write` or `delete` | The owner, and roles granted `write` or `delete` |
| Open a page | Roles whose `pages` name it (public pages: anyone) | The same |
| Run a standard action | The owner, roles granted `write` on its model, and roles whose `actions` name it | The same |
| Run a custom action | Roles whose `actions` name it | The same |
| Everything | Admins | Admins |

```yaml
roles:
  admin: all
  sales:
    description: Works with customers and orders.
    pages: all                   # every page but the administrators' (the users page, a data page), which a role gets by naming them
    create: all
    write: [Customer, Order]     # anyone's customers and orders; deleting them stays each one's own, and admins'
    actions: [mergeCustomers]    # custom or standard; a standard one also follows "write" on its model
```

- `access` on a model or a page and `allow` on an action are errors that say where it went.
- A role that opens no page is warned about (`role-opens-nothing`), unless the app has an `api` block and the role is granted something on a model the API offers: a role for keys needs no page. With `private` access, `write` or `delete` on records the role is not granted `read` on is a warning too (`write-without-read`): nothing would let it open them. `create` without `read` is fine (a form-only role).
- The operation `grant <role> <what> <names…|all|none>` sets a grant: `grant sales write Customer Order`, `grant sales pages all`, `grant sales delete none`; `grant sales all` is the whole app and `grant sales none` the record rule only. Administrators are not granted: they do everything.
- With `private` access, the short form `unique` means unique per owner: two users can both have invoice `2026-001`; `unique: owner` or `unique: app` says it outright ([Unique values](#unique-values)).
- Everything is enforced on the server, for every read and write: a record the user may not read cannot be opened, even by guessing its id, and cannot be chosen in a form.

## Semantic text

Any `app`, model, field or page may carry free text that explains **meaning** to AI and developers. It is never shown to visitors.

| Key | Meaning |
|---|---|
| `description` | What it is. On a choice field, a short one (120 characters at most) is also in the assistant's summary line, so a model reads the app's words for the values before it filters on one |
| `intent` | The outcome or experience it should achieve |
| `rules` | Domain rules as sentences. A rule does nothing by itself until something implements it; implemented rules get an id: `{ id: capacity, rule: … }` |

The Booking and Invoicing starters come with one.

`generated: true` on a picture (a hero's, a gallery's, or the logo) says an AI made it. The app then marks it, as the EU's AI Act asks of pictures that could pass for photographs: "AI-generated" (in the app's language) in the bottom right corner of a picture across the page, "AI" on a small one, such as a gallery's. A picture styled where it is used is not marked (the `cover` hero under the theme's color, the `centered` one under its veil, the `photo` one under its scrim), and the logo never is, since a mark is not a photograph. The pictures from the Smithable image library carry it; a maker's own pictures carry it only when the maker says so, and changing a picture's `src` with `setText` takes it off.

Every model, field, choice value, page and menu named here must exist in `smithable.yml`; `smithable validate` checks this. Semantic text (`description`, `intent`, `rules`) is never shown to visitors, so help text belongs here.

Libraries for custom code (`src/custom/`) are declared in `smithable.context.yml`, the one file that names technologies, with exact versions: `packages: { chart.js: 4.4.1 }`, or with the operation `setPackage chart.js 4.4.1` (`none` removes one). Smithable adds them to `package.json`; the stack profile's own packages (React, Drizzle, …) are refused, since Smithable keeps their versions in step.

A counter of visits is one line in `smithable.context.yml`, naming one provider with the app's id there: `analytics: { plausible: shop.example.com }`, `{ umami: <website id> }`, `{ fathom: ABCDEFGH }` or `{ google: G-XXXXXXXXXX }`; the operation `setAnalytics plausible shop.example.com` sets it and `setAnalytics none` takes it away. Its script is loaded in a production build only (never in development or a preview), and the app's Content-Security-Policy allows its addresses and nothing more. Plausible, Umami and Fathom set no cookie and start at once; Google Analytics waits for the visitor's yes in the consent bar ([design/analytics.md](../design/analytics.md)).

The consent bar is the kit's: shown at the bottom of every page when something asks for consent and no choice is kept, with Accept and Decline as equal buttons and a link to the page named `privacy` when there is one; the choice is kept in the browser for a year, and "Cookie settings" in the menu or the footer asks again. Its words can be changed in `smithable.content.yml` under `consent: { text, accept, decline }`. Custom code that embeds something needing consent (a map, a video, a chat widget) calls `afterConsent(run)` from `#/kit/consent`: `run` runs once the visitor has said yes, and the call makes the bar appear.

`language` is the language of the app for the people who use it: the words the app brings itself (Save, Cancel, the sign-in page, the mails) are in it, and dates and numbers in sentences the app writes follow it. The maker's own texts are as written, whatever it says. It must be a language the app kit has words in (`en` and `sv` so far; [design/language.md](../design/language.md)); in another language than English every model should give its `pluralLabel`, since the plural made by an English rule would read wrong, and `smithable validate` warns about those that do not. The operation `setLanguage sv` sets it.

`languages` lists the other languages the app is offered in (`languages: [sv]`), each one the kit has words in and none the app's own. Each has its own file, `smithable.content.<language>.yml`, with the same keys as the content file and the texts in that language: any text a person reads, the content file's own and those Smithable derives from names (a model's label and plural, a field's label, a choice's values, a page's title, an action's button). It holds texts only: no `language`, `languages` or `logo`, nor what no person reads as words (a picture's file, an address to go to, the operator's email or phone). `addLanguage` on a language listed whose file is missing writes the file again. A text left empty, or not there, shows in the app's own language, and `smithable validate` says how many there are (`text-untranslated`). `smithable op addLanguage sv` lists the language and writes its file with every text empty, to be filled in; `setText … --language sv` writes one; `removeLanguage sv` takes the language and its file away. `smithable translate sv` has the configured model draft the texts still empty (Studio's Languages tab has a button for it); they are saved with `setTexts` as one change, and undo takes it back. A renamed field or choice value follows into every language file. ([design/languages.md](../design/languages.md).) The app's own language is at `/`; each other one at its code first (`/sv/`, `/sv/menu`): a public page in Swedish is a page of its own for search engines, with the other versions named beside it, and the sitemap lists every version. Signed-in pages keep one address and show the language last chosen with the switch at the foot of each page. A text the same in several places is translated once: when two places give it different words, the app shows the first and `validate` says so (`text-shared`).

`logo` is the app's mark: a file under the app's `public/images/` (webp, avif, jpg, png or svg; square or nearly, about 512 px) and what it shows. It is drawn before the app's name in the menu and the landing page's header, and the browser's tab shows it; without it the app shows its name alone and an icon with its initial. `src` must have that form (`logo-src`) and `alt` must be there (`logo-alt`); whether the file is there is not checked. The operation `setLogo images/logo.webp --alt "A lotus"` sets it, and `setLogo` without a file removes it. An app made from a description gets one from the Smithable image library ([design/app-logo.md](../design/app-logo.md)).

The operation `setText` changes one text by its path, e.g. `setText "All our customers" pages customers subtitle` (an empty text restores the default). A list item's text is addressed by its position, e.g. `pages home faq items 0 question`. Studio uses it when a text is changed in place in the preview. `removePage` removes a page's texts along with the page and takes it out of `public.pages` and off a landing hero's button and shortcuts (its confirmation says so), and `removeSection` a landing section's; `addSection home gallery` adds a section (with `records`, `form` or `button` as its options), which Builder offers as "A section on a landing page". `addLandingPage home` makes a landing page with a hero and a footer, at `/` when that is free, and lists it under `public.pages` unless `public` is false.

## `smithable.auth.yml`: sign-in, roles and what is public

Required, next to `smithable.yml`. It is technology-neutral: no library names or keys (those are environment variables).

```yaml
smithableAuth: 0.1

signIn:
  providers: [email]             # email (a code by mail, no keys), google, facebook; the order is the button order
  allowedDomains: [acme.com]     # optional: only these email domains may sign in
  selfSignUp: false              # optional: only invited people and admins (needs a users page)

defaultAccess: shared            # shared | private; required with sign-in (see Access)

roles:                           # optional; "admin" always exists and is always all
  admin: all
  sales:                         # what the role may do beyond the record rule (see Access)
    description: Works with customers and orders.
    pages: all
    create: all
    write: [Customer, Order]
defaultRole: sales               # the role new users get; needed with several roles
admins: [owner@acme.com]         # become admins when they sign in

# ⚠ PUBLIC: visible to anyone on the internet, without signing in.
public:
  pages: [schedule]              # pages anyone may open (the sign-in page always is)
  read:
    - Session                    # models anyone may read
    - Post: { where: { status: published } }   # …or only the records with these values
    - Incident: { where: { status: [investigating, identified, monitoring, resolved] } }   # one of several
  create: [ContactMessage]       # models anyone may create, e.g. a contact form

# What other programs may reach with a key (a key is made in the app, with a role).
api:
  models: [Customer, Order]      # or all, with except: [AuditEntry] for the ones left out
  actions: [markPaid]            # the standard actions they may run, and custom actions on rows (run on ids); or all
  assistants: true               # optional: offered to AI assistants as tools too

# "Ask", the assistant in the app, for the people who use it.
assistant:
  for: [admin, staff]            # roles; or signed-in (everyone who signs in); or anyone (visitors too)
  may: read                      # read (the default) | change: it also adds, changes and runs actions
```

| Key | Meaning |
|---|---|
| `signIn` | `none` for an app without sign-in (then only `public` is reachable), or `providers` with optional `allowedDomains` and `selfSignUp` (`true` by default; `false` lets only invited addresses and the `admins` sign in, and needs a [users page](#users)). `setProviders email google` sets the providers, in button order; `setDomains acme.com` sets `allowedDomains` (`setDomains none` lifts it) |
| `defaultAccess` | `shared` or `private`: the default access to records ([Access](#access)). The operation `setDefaultAccess shared` sets it |
| `roles` | Role names (camelCase), each `all` (the whole app) or a block: an optional `description` and the grants `pages`, `read`, `create`, `write`, `delete`, `actions` and `review` (the models whose waiting files the role approves or rejects, [Review](#review)), each a list of names or `all` ([Access](#access)). `admin` always exists and is always `all`; so does a role for everyone else, `member`, when none is named. The operation `grant <role> <what> <names…>` sets a grant |
| `defaultRole` | The role new users get; never `admin` (that would make everyone who signs in an administrator: an error) |
| `admins` | Email addresses that get the `admin` role when they sign in with the address proven, also an address added after its account was made, and may always sign in. `setAdmins you@your-domain` sets them; `smithable new` puts in `--admin` or the Git user's address. A warning says when only invited people may sign in and there is no administrator (nobody could), and when an address is on a domain nobody receives mail at (`.example`) |
| `public` | `pages`, `read` and `create`: what anyone may open, read or create without signing in. A public page shows a visitor only records of models under `read`: `smithable validate` warns when a public page shows a model that is not there (its list or its cards would be empty). A model in `read` may be limited to records with certain values, `Post: { where: { status: published } }` (a choice field's value or a list of them, or a yes/no field's `true` or `false`): visitors, and signed-in people who read only because it is public, see those records everywhere (lists, searches, cards, references), while roles that may read the model and a record's owner see the rest as before. Removing the field or the value is refused until the condition is changed. The operation `setPublicWhere Post status=published` sets it (several values as the choices are written, `"status=investigating | identified"`), and `setPublicWhere Post` lets visitors read every record. Who owns a record (the owner the app keeps) is told only to its owner and to roles that read every record, never to a visitor or another member. The app's `/robots.txt` lets search engines read the public pages (with their scripts, styles and pictures) and refuses the rest (everything, when nothing is public). |
| `api` | What other programs may reach with a key: `models` (a list, or `all`, which also offers models added later, as `setApi` and the summary say, with `except` for the ones left out), `actions` (standard actions of offered models, a list or `all`) and `assistants` (`true` to offer the same to AI assistants as tools; `{ delete: true }` lets them delete too). Nothing is offered unless it is said here. Listing is not granting: a key is made in the running app by an administrator, with a role, and that role's access decides what the key may do, exactly as for a person. `api` needs sign-in. A warning names offered models with personal data. The operation `setApi Customer Order --actions markPaid` sets it (`setApi all --except AuditEntry`; `setApi` alone turns it off). The app serves it under `/api/v1` with its description at `/api/v1/openapi.json`; [Let other programs use your app](https://docs.smithable.ai/api.html) walks through it. With `assistants`, the same is offered as tools for AI assistants at `/mcp`; they may delete only with `assistants: { delete: true }` (`setApi … --assistants true --assistants-delete true`) and a key whose role may delete. Without a key, a program or assistant is a visitor: it may list and read the offered models that `public.read` lets anyone read (with their `where`) and add to those `public.create` lets anyone add, never change, delete or run an action; the description and the tools show it only that (a key or a session that may open the users page sees the whole description), and with nothing public every call needs a key and the description names nothing |
| `assistant` | "Ask", the assistant in the app ([design](../design/assistant.md)): `for` is the roles that get it (`[admin, staff]`), or `signed-in` (everyone who signs in), or `anyone` (visitors too, who are answered by the app's wording rules over what is public and never by a model); `may` is `read` (the default: it finds, counts and adds up) or `change` (it also adds, changes and runs standard actions, each confirmed by the person; it never deletes). It acts as the person asking, so it reaches what they may. Without the block the people who use the app do not get it. The operation `setAssistant [roles… \| signed-in \| anyone] [--may read\|change]` sets it; with nothing it is switched off |

`smithable validate` warns about risky combinations, and never changes their meaning: `shared` access with open sign-up and no `allowedDomains` (anyone with an account at the provider can sign up and read everything), and public reading of models with personal data (`email`, `phone` or `User` fields). Everything named in `public` must exist in `smithable.yml`, and every role used there must exist here.

In development, the sign-in page also offers signing in as any role, without contacting the provider. Production builds leave that out.

```yaml
    icon: users                                  # its icon in navigation (optional)
    filters: { shown: [segment, creditLimit] }   # the filters shown when the list is first reached; the rest fold behind "More filters" (one with a value in the address shows anyway)
    table:
      columns: [name, email, segment]            # which fields the list shows, in order; without it: the title, a picture, the required fields, then the rest, five at most, no long text unless the model has no short text to be titled by
      below: { email: phone }                    # a second field under a column's value
      sort: -creditLimit                         # the order until someone sorts; "-" for largest or latest first
      view: cards                                # cards on wide screens too (table by default)
    record:
      lists: { orders: table }                   # a list on the record page: table (default) or thread
      subtitle: email                            # the line under a record's name on cards and in pickers: a name part
      detail: [segment, creditLimit]             # smaller parts after it
    form:
      fieldOrder: [name, email, phone]           # these first; the other fields follow (or sections, not both)
      sections:                                  # groups with headings; fields in none follow at the end
        - { name: contact, fields: [name, email, phone] }
        - { name: terms, fields: [creditLimit, segment] }
      columns: 2                                 # short fields two abreast on wide screens
      control: { creditLimit: slider, segment: radio }   # how a field is entered
  mortgage:
    form: { results: below }                     # a calculator's results under its inputs
  about:
    frame: site                                  # site | app | none: the public frame, the workspace, or the page alone
  home:
    theme: { preset: playful, brand: { font: Nunito Sans } }   # a landing page's own theme
    header: { position: scrolling }              # sticky | scrolling: the header kept at the top as the page scrolls, or away with it (sticky)
    sections:                                    # a landing page's sections' looks, by section name
      hero: { layout: split, image: left }       # split | centered | plain | cover | photo; the picture's side
      features: { columns: 4 }                   # 2 | 3 | 4 | 5 | 6 (3)
      classes: { layout: grid, columns: 6 }      # records: cards | list | grid; columns 2–6 (cards 3, grid 4)
      testimonials: { layout: carousel }         # cards | carousel | one
      pricing: { highlight: Pro }                # the plan drawn forward, by its name
      faq: { layout: list, columns: 2 }          # accordion | list; a list's columns 1 | 2 (1)
      gallery: { columns: 4 }                    # 2 | 3 | 4 | 5 | 6 (3)
      callToAction: { band: primary }            # any section but the hero and footer: none | muted | inverse | primary (none)

tones:                                       # colors of choice values, by meaning
  Order.status: { shipped: success, canceled: danger }   # success | warning | danger | neutral

aiBadge: false                               # no badge on pictures an AI made (on by default)

assistant: { voice: friendly }               # Ask's manner: plain (the default) | friendly | formal
```

- `primary` is a color like `"#1d4ed8"`. The theme derives its colors from it and adjusts its lightness where needed, so text on it stays readable in light and dark mode.
- `background` is a color like `"#f5efe6"` for the page behind everything: a pale wash of it in light mode and a deep one of the same hue in dark mode, quiet enough for text. Cards, borders and muted text are derived from it again, while the primary, the states and the charts stay the theme's. A color the theme's text could not read on is warned about and not used. In Studio: Look → Color → Background.
- `font` is one of Inter, Nunito Sans and Source Sans 3: open-license fonts the app hosts itself. Without it, the preset's font is used (Inter for modern and minimal, Nunito Sans for playful, Source Sans 3 for corporate).
- `density`: `comfortable` is the default for apps that do not say, `compact` makes controls, rows and padding smaller, for data-heavy tools, and `standard` sits between them. One density per theme: a landing page's own theme gives the public pages theirs, so "customer pages comfortable, staff pages standard" is a page theme with `density: comfortable`. Touch screens keep 44 px controls whatever the density.
- `record.subtitle` and `record.detail` are the lines under a record's name on the page's cards and in reference pickers ([design/record-names.md §3](../design/record-names.md)): the same parts as a model's `namedBy` (a field, a reference, a field one reference away), read by the same formatter; a page that says nothing shows the name alone. `setRecordLines sessions instructor.name --detail classType.level` sets them; `none` and an empty list take them away.
- `below` shows a second field under a column's value, like the phone number under the email; the column's heading names both.
- `frame` is the frame a page shows in (docs/design/page-sections.md §4): `site`, the public frame with the app's name, a top menu and the site's footer; `app`, the workspace with the side menu; `none`, no menu and no header, for a screen that stands alone. Without it, the page kind's own: landing and articles pages `site`, the rest `app`. The frame is the page's, never the role's: staff open a `site` page from the workspace and see it as members do. `setFrame about site` sets it; `default` returns to the kind's.
- `filters.shown` names the page's filters (from `smithable.yml`) that show at once; the others fold behind "More filters" until wanted, a folded one with a value in the address showing anyway. Without it every filter shows. `setFiltersShown customers segment creditLimit` sets it; with no fields it is removed.
- `theme` on a landing page (only there: it has its own frame, while a list page in another theme would look like another app) changes the keys it names from the app's theme, with the same keys (`preset`, `brand`, `density`, `motion`). Its font is installed too. `setTheme --page home preset playful` sets one, and `none` returns a key to the app's; for `motion`, `none` is a value (no motion), not a return.
- `sections` (a landing page only) gives a section a look. A hero is `split` (the text beside its picture, `image: right` or `left`), `centered` (the text over the picture), `cover` (the picture across the width, the theme's primary color washing over it behind the text; in dark mode the dark background tinted with the primary, under the page's own text color), `photo` (the picture across the width at least 80% of the window's height on a wide screen, a dark scrim from the start side, the text and buttons at the start; on a phone the scrim rises from the foot, where the text sits; the text is always white on the scrim, in light and dark mode alike, so it reads whatever the theme) or `plain`; without a picture every hero is plain. Features and a gallery have `columns`, how many stand side by side on a wide screen (2 to 6; 3 when not said; fewer on a phone); a records section is `cards`, `list` (rows with a small picture) or `grid` (the pictures, titled), with `columns` (2 to 6) for cards and a grid, 3 for cards and 4 for a grid when not said (a list has none: columns there are a warning); testimonials are `cards`, a `carousel` that scrolls sideways, or `one` large quote; a pricing section's `highlight` names the plan drawn forward; a FAQ is an `accordion` or a `list` with every answer shown, a list in `columns` 1 (the default) or 2 (columns with the accordion are a warning: it is one column). Every section but the hero and the footer (features, records, pricing, testimonials, faq, callToAction, contact, gallery, text, calculator) may have a `band`: `none` (the default, an open section), `muted`, `inverse` or `primary`, the section across the window's width on that surface of the theme (`muted` the theme's muted surface under the page's text; `inverse` the text color as the surface, the background's color as the text; `primary` the primary under its own text color), its content in the page's measure. Inside a band the text, cards, buttons and links take the band's colors: on `inverse` and `primary` every text is the band's text color, cards and lines are a step from the surface, and a button turns inverse (the band's text color as its fill). A band whose text would read under 4.5:1 on its surface in the page's theme, in light or dark mode, is a warning (`band-contrast`); the built-in themes' bands all read, and a brand primary's text color is chosen to read on it. A section of your own (`custom`) draws its own frame and has none. On a page in the app's frame a band stays in its column. `setSectionLook home gallery columns 5` sets one, `default` removes it. Removing a section removes its look.
- `header` (a landing page only) is the look of the page's header, the frame's top row with the app's name and menu, not a section. Its `position` is `sticky` (the default: it stays at the top while the page scrolls, on the theme's card color with its bottom border, on a phone too; a section reached by its link stops below it) or `scrolling` (it goes up and away with the page). Each landing page says its own. `setSectionLook home header position scrolling` sets it (the header is named like a section; a section of the page named `header` takes the name first), `default` removes it.
- `results` (a calculator page's `form` only) is `beside` (the default: next to the inputs on a wide screen) or `below`. A phone always shows the results under the inputs.
- `icon` is one of users, user, file, receipt, cart, package, calendar, layers, book, briefcase, building, chart, clipboard, home, mail, settings, star, tag, truck and list. Without it, one is chosen from the name of the page's model (Customer: users, Invoice: file, Session: calendar; list when nothing fits).
- `aiBadge` switches the badge on pictures an AI made (see the content file's pictures) on or off: the badge is on unless you switch it off; whether your audience needs it is your responsibility. `setAiBadge false` switches it off, `setAiBadge` on again.
- `assistant`'s `voice` is Ask's manner, a fixed set of lines given to its model: `plain` (the default: short, no pleasantries), `friendly` or `formal`. Its texts are the content file's, who gets it the auth file's. `setAssistantVoice friendly` sets it.
- `tones` name a choice field as `Model.field` and give some of its values a meaning (`success`, `warning` or `danger`), which the app shows as the badge's color. Values not listed are `neutral`.
- Every page and field named must exist in `smithable.yml`; computed fields can be columns but not in a form. Renaming or removing a field updates this file, and so does removing a choice value.
- `control` chooses how a field is entered: `slider` (a number with `min` and `max`), `stepper` (a whole number), `radio` (a choice of at most five values, or a yes/no), `select` (a choice or a reference), `combobox` (a reference), `textarea` (a text), `switch` (a yes/no); `input` is the default for its kind. A control that does not fit its field is an error. A calculator page's fields take one too.
- `sections` group the form under headings, whose texts are in `smithable.content.yml` (`pages.customers.form.sections.contact: { title: How to reach them }`; the name otherwise); `columns: 2` puts short fields two abreast, long texts and pictures full width. `sort` and `view` shape the list.
- `record.lists` shows a list of related records on the record page as a `thread`: a conversation with a reply box, for messages, notes or remarks (`lists: { messages: thread }`), instead of a table. The thread reads the listed model as its `thread` key says (`Message: { thread: { body: content, author: sender, side: { field: sender, ours: agent } } }` in `smithable.yml`), and what that leaves out by rule: its first long text field (`text` or `markdown`) is the message, its first field that refers to a person (else its first email) the writer, `createdAt` the time, its files and pictures the attachments, and its first two-valued choice the side, the first value being ours (`sender: agent | customer`). Where the rule has several fields to pick from, `smithable validate` warns (`thread-ambiguous`) and names the words to write; `setThread Message --body content --author sender --side sender --ours agent` writes them (`--none` removes them). A model with no long text field cannot be a thread. `smithable validate --explain` says what every such rule settled: each model's title field, where its unique values are unique, what a conversation reads, and who may run each action. The reply box adds a record by the ordinary create, the reference back filled in, so every other required field needs a default or `by: app`; one that has neither is a warning (`thread-needs-form`). `setRecordList customers notes thread` sets it.
- The operations `addTheme` (a theme of the project's own, `--use` to apply it), `setTheme`, `setColumns`, `setFieldOrder`, `setTone`, `setIcon`, `setBelow`, `setControl`, `setFormSections` (each section `name:field,field`), `setFormColumns`, `setView`, `setFiltersShown`, `setFrame`, `setSort` , `setRecordLines` and `setSectionLook` change it.
- `preset` is one of the nineteen built-in themes, or one of the project's own (see [Themes](#themes)).

### Themes

A theme is data, never CSS: a font, a corner radius, a shadow and the colors the app uses, in light and dark mode. The mode shown is the visitor's: System (the device's setting) unless they chose Light or Dark under Appearance, kept in their browser and applied before the page first paints. The nineteen presets are themes Smithable ships (listed below); a project's own go in `themes/<name>.yml` (written through `addTheme <name> --text @file [--use]`, refused with the file's problems) and `theme.preset` names either. `smithable theme --from <url> [--name x] [--use]` makes one from a site: a browser (Playwright) reads its background (the page's own before its bands), text, primary button color (a link styled as a button counts), cards, corners and font (a hosted font by its own name, its headings' too when they differ) in light and dark, in any CSS color (Tailwind 4's `oklch` too), with the dark mode a page switches by a class (`.dark` or `data-theme="dark"` on `<html>`) when the device's setting changes nothing; it derives the rest, raises contrast where it would not read, and adds it with `addTheme`.

The built-in themes, each in light and dark:

| Preset | What it looks like |
|---|---|
| `modern` | indigo on a cool white, rounded, Inter; the default |
| `minimal` | near-black on a warm white, quiet colors, light borders, Inter |
| `playful` | bright violet, very round, pill buttons, Nunito Sans |
| `corporate` | muted teal on a cool grey-white, square corners, compact, tabular numbers, Source Sans 3 |
| `coastal` | deep teal on warm sand, rounded, soft shadows, Nunito Sans |
| `navy` | deep blue on a cool white, square corners, compact, Source Sans 3 |

| `nordic` | petrol blue on a cool white, calm, soft shadows, Inter |

The first four come from the design delivery. The other fifteen (the theme lab's three styles, then three from a tester's report) are theme files like a project's own, kept inside Smithable and checked the same way; a project may still have a theme of its own under any other name (`forest`, say).

```yaml
# themes/forest.yml
smithableTheme: 0.1
name: forest                   # kebab-case; the file's name when left out
fonts:
  body: Nunito Sans            # a hosted font: Inter, Nunito Sans, Source Sans 3, Source Serif 4, Fraunces, Archivo Narrow, DM Sans, Outfit
  heading: Fraunces            # optional: the headings' font; the body font when left out
radius: 12px                   # corners: a length in px or rem
shadow: soft                   # none | soft | raised
motion: subtle                 # optional: none | subtle (default) | lively
density: comfortable           # optional: comfortable (default) | standard | compact
chroma: 0.22                   # optional: how much color a brand color keeps on this theme (0–0.4)
headings: { weight: 600, tracking: normal, scale: large }   # optional, like the groups below
surfaces: { cards: flat }
light:
  primary: "#2f6b3a"
  background: "#f6f8f4"
  foreground: "#1f2a1f"
dark:
  primary: "#8fd19a"
  background: "#141a14"
  foreground: "#e6ece4"
```

- Each mode needs at least `background`, `foreground` and `primary`; the other 25 colors (`card`, `muted`, `accent`, `border`, `ring`, `destructive`, `success`, `warning`, the charts, and every `-foreground`) may be given or are **derived** the way a brand color is: the text on a color is whichever of dark and white reads better, muted and secondary step the background towards the foreground, borders a step further, the accent tints the background with the primary, the focus ring is the primary (a step towards the text where a bright one would not show on a card), the charts spread around the primary's hue. Colors are `#rrggbb` or `oklch(L C H)`.
- The **style** of a theme is a few groups of fields, each from a fixed set of values, never CSS; what a theme leaves out is the default (given first):
  - `headings`: `weight` 400–800 in hundreds (700), within the heading font's own range (Archivo Narrow goes from 400 to 700), `tracking` `tight` | `normal` | `wide`, `scale` `regular` | `small` | `large` (the size of page and section titles), `case` `none` | `upper` (the landing page's and the frame's titles only, never a record's name; capitals need `normal` or `wide` tracking), `align` `start` | `center` (a landing section's eyebrow, title and lead, at the start or centered over the section; a hero keeps its own layout).
  - `surfaces`: `cards` `bordered` | `raised` (a shadow) | `flat`, `sections` `open` | `boxed` | `banded` (a landing page's sections alternate: counting the sections after the hero that show and can have a band, the second, fourth and so on are on the `muted` band, unless a section says its own `band` in the ux file; the footer is not counted), `dividers` `light` | `strong` | `none`.
  - `buttons`: `shape` `rounded` | `pill` | `square`, `weight` `regular` | `bold`.
  - `pictures`: `corners` `theme` | `square` | `round`, `frame` `none` | `border`.
  - `tables`: `numbers` `normal` | `tabular`, `rows` `lined` | `zebra` | `plain`.
  - `font` (the body font alone) still reads; naming it and a different `fonts.body` is an error.
- A theme is **checked** like the built-ins: every pair the app puts together (text on background, card, primary, muted, accent, badges) must reach 4.5:1 and the focus ring 3:1 against the card; a theme that does not read is an error naming the pair and its ratio.
- `smithable themes` lists the themes the ux file may name; `smithable validate` checks the project's. A project theme with a built-in's name replaces it for that project. Studio shows every theme with a picture drawn from its colors.
- `smithable theme lab [--project <dir>] [--port 4330]` opens the theme lab: the theme's fields as controls and as the file's text, beside a booking app's landing page, list, form and record in light and dark, with the fit lines and the check's errors under them; Save adds the theme through `addTheme`. The how-to [Make a theme](https://docs.smithable.ai/theme.html) makes one both ways.
- A theme ships no CSS, components or fonts from elsewhere, so switching themes is always safe and the hosted service can offer them without vetting code.

## `smithable.context.yml`: how the app is built

The one file that may name a technology. It says how the app is built, never what it does: a functional requirement belongs in `smithable.yml`, a look in `smithable.ux.yml`, a text in `smithable.content.yml`.

```yaml
smithableContext: 0.1
adapter: tanstack                 # the stack profile (one so far) and its database
database: sqlite
conventions:                      # read by a model that writes custom code or a plugin
  - Prefer existing components before creating new ones.
guidance: >
  Tables should be compact; this is a back-office tool used all day.
plugins: [newsletter]             # project plugins, see "Sections Smithable does not know"
packages: { chart.js: 4.4.1 }     # libraries for src/custom/, at exact versions
analytics: { plausible: shop.example.com }   # a counter of visits, one provider
ai:
  policy: best-available          # local-only | eu-only | best-available (the default) | custom
```

- `adapter` and `database` name the stack profile the app is generated with; the generated code follows that stack's own idioms.
- `conventions` (a list) and `guidance` (free text) are preferences for the code a model writes for the project, custom pages and plugins; they never change generated code, and they never hold functional requirements.
- `plugins` declares the project plugins whose sections `smithable.yml` may use.
- `packages` declares the libraries custom code may import, at exact versions; `setPackage` adds or removes one, and the stack profile's own packages are refused (the content section above says why).
- `analytics` names one counter of visits with the app's id there; `setAnalytics` sets it. The cookie-free providers start at once; Google waits for consent.
- `ai.policy` says where a model may run for this project ([ai.md](../ai.md)): `local-only`, `eu-only`, `best-available` (what nothing said means) or `custom` with `allow` listing the providers by name.

The file is checked against its JSON Schema (`CONTEXT_SCHEMA` in core): `smithableContext: 0.1` and only the keys above. `smithable validate` reports a problem on its key, and an operation that changes the file is refused if it would leave it invalid.

## Sample data

A project may give its models sample records in `samples/<Model>.yml`, beside `themes/`: a list of records with the model's field names as keys. `pnpm db:seed` (and `smithable new`) adds them instead of generated ones; a model without a file still gets generated records.

```yaml
# samples/ClassType.yml
- name: Hatha
  summary: Slow, steady postures held for a few breaths each.
  level: allLevels                    # a choice by its value or its label
  price: 16.50                        # money as an amount
  instructor: Emma Lindqvist          # a reference by the record's title (samples/Instructor.yml)
  photo: { file: hatha.webp, alt: A class stretching }   # a file in public/images/samples/
```

- Dates are written `2026-10-05`, dates with times `2026-10-05 08:00`. A calendar's records are moved to this week and the next, keeping their weekday and time.
- A reference names the other record by its title, which needs the other model's sample file; without one, give the number of a generated record (1 for the first).
- A picture is a file name under `public/images/samples/`, or `{ file, alt }`; without `alt`, it says what the record is. `{ file, alt, generated: true }` says an AI made it, and the app marks it where it shows it ("AI" in a corner; see the content file's pictures); the numbered pictures (`0.webp`, `1.webp`, …) seeded where a model has no sample file are the image library's and always are.
- `smithable validate` checks the files: an unknown model or field, a value of the wrong kind, a missing required field, a reference to a record that is not there. Lists of related records and calculated fields are not set in samples.
- `smithable new --no-sample-data` starts with no `samples/` folder and an empty database.
- `samples/people.yml` is the sample users (docs/design/sample-users.md): a list of people with a `name`, a `role` of the auth file or `visitor`, a `persona` in a sentence and a `pace` in minutes between moves (1 unless said). They act only in a development or demo build, through the app's own forms and actions as that role, and go with the sample data; a published app never has them. The file is written by the operations `addSampleUser <name> <role> [persona…]` (`--pace` for the minutes; without a persona, the role's description) and `removeSampleUser <name>`, at most five people; a role a sample user has cannot be set away.
- `samples/ask.yml` is the app's own Ask check (docs/design/ask-words.md §4): a list of questions a person with a `role` (one of the auth file's, or `visitor`) would ask the in-app assistant, each with `expects`, the shape of the answer: the `kind`, a `where` (field to value, list of values or range) or a `measure` (a number field), and `answer`: `count`, `names` or `number`. Written by Smith's question pass and editable by hand. A kind, field, value or role it names that is no longer in the spec is a warning naming the line, and the question stays as written, so a rename leaves nothing silently broken; the sample validators leave the file alone, like `people.yml`, and it goes with the sample data.


### Importing records

Existing records come in from a spreadsheet saved as CSV: `smithable op importRecords Customer --from customers.csv` (in Studio: Change → Records from a CSV file).

- The first row names the columns. A column fills the field whose name or label it matches, ignoring case, spaces and underscores (`Credit limit` fills `creditLimit`); `--map "Company=name,Mail=email"` names others. Columns that fill no field are left out and listed; pictures, calculated fields, lists of records and people who sign in are not imported.
- Values are read like sample data: an amount in units (`12.50`, `12,50` or `1 200`), a date as `2026-10-05`, a date and time as `2026-10-05 08:00` in the app's time zone, yes or no (`true`, `yes`, `1`), a choice by its value or label, a reference by the referenced record's title (exactly one must match). An empty cell is the field's default, or no value. A file with `;` between columns (a spreadsheet set to a decimal comma) is read too.
- `--dry-run` shows the first five records as they would be stored and every problem, each with its line. Without it the records are added in one go, at most 10,000: any problem (a required value missing, a value of the wrong kind, a reference that matches nothing or several records, a unique value already taken) adds none and says where.
- The import is one change: `smithable undo` takes the records back. The records belong to the first admin who has signed in, or to the user `SMITHABLE_IMPORT_OWNER` names (an id or email; the hosted service sets it to whoever imports), and the dry run says whom; the model's hooks do not run.

## Not supported

Smithable specs are plain data. YAML anchors (`&name`), aliases (`*name`) and tags (`!!str`) are rejected, because they make specs hard to read and unsafe to edit automatically.
