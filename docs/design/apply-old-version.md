# Applying an old version

Design, 2026-11-20. Not built. The core contract for the eighth build of the preview-first Studio (studio-preview-first.md, "History you can try before applying"): a person looks at an earlier version of the app and makes it the current one. Looking is designed in old-version-preview.md; this note is only about **Apply this version**.

## 1. What a version is

Every change is a commit made by the operation layer, with the files it ended with, its migration, and a snapshot of the development database taken before it. Nothing is rewritten: an undo is a new commit that reverts an earlier one. So a change that was undone is still in the history.

- **A version is a commit on the project's main line** (first parents of the project's own branch). A held fix lives on a `fix/<id>` branch in the same folder: its commits are not versions, and Apply is refused while the project stands on one.
- **No new storage.** "Alternate versions" (B, after B was undone and C made) are commits on the same line. There are no branches of versions to keep, merge or clean up.
- **The definition has no retention period.** A version's definition can be applied for as long as its commit is in the repository. What has a lifetime is the database snapshot, which only *looking* uses (the copy "with the data from then", or with samples when the snapshot is gone). Apply never reads a snapshot (§3), so a version stays applicable after its snapshot is deleted. The Studio note left retention open for Johan; this is the answer proposed to him.

## 2. The rule

**Applying a version is a new change whose managed files are that version's managed files. It goes through the same pipeline as every operation: validated, written, regenerated, migrated forward from today's database, committed.** It is never a checkout, a reset or a revert of commits, and the old generated code and old migrations are never brought back.

It follows that:

- today's records stay, and are carried to the old shape by a new migration, like any change of shape;
- the result is generated by today's engine and kit, not by the code of then: applying a version from before a fix does not bring the bug back;
- B, C and everything between stay in the history, and the Apply itself is one more entry.

The database here is the project's development database, as for every operation. The published app is not touched: its records meet the new shape when the owner publishes, with the Release checks, as after any change.

## 3. What comes back, and what does not

The **managed files** are one list, used by the plan, by its validation and by a later undo alike:

| Part | Applied? | Why |
|---|---|---|
| `smithable.yml`, `.ux.yml`, `.content.yml`, `.context.yml` | Yes | The app's definition. |
| `themes/`, the language files | Yes | The definition names them; an old look or text does not validate without them. |
| `samples/` (sample records and sample users) | Yes | They are checked against the models and roles; today's samples beside an older definition can name a field or a role that is not there. |
| `smithable.auth.yml`: roles and rules | Yes, shown apart | What each role may do is part of what the app did then. |
| `smithable.auth.yml`: `admins`, `signIn` (providers, allowed domains, self sign-up), `api` | **No: today's are kept** | These say who gets in. An address removed from the admins, a domain taken off the list, or an API that was closed must not come back by a restore. The plan's auth file is the version's roles and rules with today's values for these keys. |
| Records, uploaded files | **No** | They are today's. The copy in the old-version view may show the data from then; applying never takes it. |
| `src/custom/**` | **No** | The owner's code, outside what operations write. |
| Who may open the project (the service's members and invitations), secrets, the environment's settings, the published app | **No** | None of it is in the managed files. |

A managed file the version did not have and the project has now is removed by the change, so the result is the version's definition with nothing left over.

**Access can still widen through roles and rules**, and the people it concerns are today's: an old rule that let everyone read a model, or a role that came back and that a signed-up person still holds. So the confirmation has an access block of its own, first, listing every difference in plain words ("Anyone can read Orders again", "The role Trainer comes back; 3 people have it"), computed from the version's rules against today's role assignments. When no rule or role differs, the block is absent.

## 4. The checks, in order

All of them run before anything is written, under the project's mutation lock, and again at Redo (§6). A refusal changes nothing, names its reason in a sentence a person can act on, and leaves the version in the list.

1. **The project stands where the person saw it.** Studio sends the revision it had when the version was opened; the host compares it with the revision now. (`runFilesChange` falls back to the revision at the call, which checks nothing: Apply always passes one.) A new message: "The app changed while you were looking. See the latest change, then apply again."
2. **History, a clean folder, the main line.** No history is refused before anything initialises one; uncommitted edits and a project standing on a fix branch are refused.
3. **The version's commit can be read**, else "This version is no longer stored."
4. **The result is valid.** The plan's files are validated by today's validators against each other: the UX file against the version's themes (not the ones on disk), the content file against the version's language files, the samples against the version's models and roles, all with today's plugins. `runFilesChange` does not validate by itself; this is the undo's own check, widened to the managed files, and Apply calls it first.
5. **Nothing is lost from the records.** The difference between today's shape and the version's is worked out as effects, not as two file texts, so that it gets the same checks as an operation:
   - a stored field or a model that is gone, counted with the existing value count: an empty column goes without a question; one with values is a loss;
   - a field with the same name and another type, or a relation that changed its target: the operation layer's own conversion check;
   - a choice value that is gone and in use.

   **A rename is not guessed.** A version from before "phone → mobile" has `phone` and no `mobile`; by shape alone that is a loss of `mobile`. The host reads the recorded operations between the version and now (each commit's `Smithable-Op`): where the fields and models that differ are explained by recorded renames, the migration renames back; where they are not, it is a loss. A rename back onto a name that a newer field has taken (`phone` renamed to `mobile`, then a new `phone` added) is two things at once, the newer field going and the older coming back under its name: the newer field's values are the loss, and the migration drops it before it renames.

   On a loss Studio refuses and lists it: "This version has no place for: Instructor · phone (41 values)." The command line asks, and takes `--yes`, as for every change that loses data. The check is made again inside the migration's own transaction, since a record can arrive without the project's revision changing.
6. **Nobody is left with a role that is gone.** A role the version does not have, and that a person in the development database holds, is refused by Studio with the role and the count ("The role Trainer is not in this version; 3 people have it"); the command line asks, and with `--yes` those people are left without that role, as when a role is removed by its own operation.
7. **It would change something.** A version whose managed files equal today's is not offered.

If a later step fails (writing, generating, migrating, the commit), the pipeline's existing rule holds: every file is put back as in the last commit and the database's snapshot is restored.

`src/custom` is not checked by a rule of its own: whether the owner's code still fits the definition is found the way it is after any change.

## 5. The record

The commit is recorded as `restoreVersion` with the version's commit as its argument, and a subject that says what a person did: `Applied the version from 12 November, 14:02 (after "Instructors: added a phone")`.

`restoreVersion` is a host operation, like `undo`: it needs the history, which only a host package reads. It is not in core's registry (an entry there needs an apply step, and this one has none that core could run). The host lists it beside `undo` and `redo` for the command line (`smithable apply-version <change> [--check] [--yes --plan <digest>]`; `restore` is taken by backups), the MCP tools (`smithable_apply_version`) and the operations page. `--check` and the first refusal name the plan by a digest (the version, the files, the access block, what comes back and goes, the values lost and the roles taken, not their counts); `--plan` binds the yes to it, and a plan that changed since is refused and shown again with its new digest. Through MCP an agent answers for the user, so `confirm: true` counts only with `plan`; on the command line `--yes` alone still answers in advance, and what goes is said as it goes.

What the build changes in the host:

- `FilesPlan` and the undo's `EDITABLE` list become the one managed-files list of §3, so that a plan can add, change and remove theme, language and sample files, and an undo of an earlier change reverts the same set.
- The list of versions is its own reading of the main line: every change, the undone ones included (`undoableChanges` leaves those out, and they are exactly what "alternate versions" are).

## 6. Undo and Redo

- **Undo of the Apply while it is the newest change** is the ordinary undo: the commit reverted, the development database back at its snapshot from before the Apply. Records made in the development database after the Apply go with it; that is today's rule for every change, and the confirmation of that Undo says it when there are any. When the snapshot is gone, the bare revert would leave the files and the database apart, so the undo takes the other path instead: a new change with the earlier files, migrated forward. That path brings a dropped column back empty, so when the Apply lost values (it was confirmed with `--yes`) and its snapshot is gone, the Undo says so before it runs: the values do not come back.
- **Undo of the Apply later** is the three-way path of any earlier change, over the managed files.
- **Redo** is offered by the existing rule: only while no other change came after the undo. It does not replay through the operation registry: the host rebuilds the plan from the recorded commit and runs every check of §4 again, with today's records and today's access. It asks again on a loss; it never runs with the answer already given.
- After `apply B → undo → C`, Redo of the Apply is gone, and B is still in the list to apply again.

## 7. In Studio

The history list and the isolated viewer are the seventh build. This build adds **Apply this version** to the viewer's bar and to the entry in the list:

1. A click asks for the check. Studio shows what Apply would do, worked out from the difference between today's managed files and the version's (not from the descriptions of the changes between, which can name things Apply does not touch, such as records an import added): the access block of §3 first, then what goes and what comes back, then "Your records stay as they are." or the refusal of §4.
2. Confirm makes the change. The old-version tab closes, the preview shows the app as it now is, and the list has a new first entry, marked current, that names the version it applied. That version keeps its own entry and its "undone" label where it had one.
3. Undo is offered at once, as after any change.

Where looking at old versions is not offered (the hosted service today), Studio does not offer Apply either: a person should not apply what they could not see. The command line and MCP have it everywhere.

## 8. What must hold, and its tests

1. A → B → undo B → C → apply B: the managed files equal B's except the kept auth keys; B's and C's commits are still in the history; reopening the project shows the same.
2. Records made after B are present after the Apply, with their values in every field both shapes have; a field renamed since B has its values under the old name.
3. An address removed from `admins`, a domain removed from the allowed list and a closed API are still removed, closed after applying a version that had them. A rule that widens reading is in the access block, and a test signs in as a removed person and is refused.
4. Undo right after the Apply gives the files and the database of just before it; Redo gives the Apply again, and asks again when records would now be lost.
5. Undo of the Apply after a later change takes its theme, language and sample files back too.
6. Each refusal of §4, and a failure forced at each later step, leaves the folder, the database and the history byte-identical.
7. Applying a version made by an older kit produces today's generated files for that definition, the same bytes as making that definition fresh (rule 6 of the project).
8. A stale revision is refused; two requests at once make one change; a project on a fix branch is refused.

## 9. Not in this note

Applying a version to the published app directly; applying a part of a version (one page, the look alone: the undo of a single change and the look gallery cover those); bringing back records from a snapshot (restore from backup, its own flow); a grammar upgrade step for versions written for an older spec version (there is one version today; the step is designed with the second).
