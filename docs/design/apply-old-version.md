# Applying an old version

The core contract for the eighth build of the preview-first Studio (studio-preview-first.md, "History you can try before applying"): a person looks at an earlier version of the app and makes it the current one. Looking is designed and built (old-version-preview.md); this note is only about **Apply this version**.

## 1. What a version is

Every change is a commit made by the operation layer, with the files it ended with, its migration, and a snapshot of the development database taken before it. Nothing is rewritten: an undo is a new commit that reverts an earlier one. So the history is one line, and a change that was undone is still in it.

That settles two things the Studio note left open.

- **No new storage.** A version is a commit of the project's own repository. "Alternate versions" (B, after B was undone and C made) are commits on the same line, shown with a label that says they were undone. There are no branches to keep, merge or garbage-collect.
- **No retention period for the app's definition.** A version can be applied for as long as its commit is in the repository, which is as long as the project exists. The database snapshots are a different matter and are not used by Apply (§3), so their retention does not limit it.

## 2. The rule

**Applying a version is a new change whose files are that version's files. It goes through the same pipeline as every operation: validated, written, regenerated, migrated forward from today's database, committed.** It is never a checkout, a reset or a revert of commits, and the old generated code and old migrations are never brought back.

This is the path an undo of an earlier change already takes (`runFilesChange`, a change given as the files it ends with). Apply differs only in where the files come from: the whole of each file as it was at the version, not a three-way merge that takes one change out.

It follows that:

- today's records stay, and are carried to the old shape by a new migration, like any change of shape;
- the result is generated by today's engine and kit, not by the code of then: applying a version from before a fix does not bring the bug back;
- B, C and everything between stay in the history, and the Apply itself is one more entry;
- Undo after Apply puts back the state just before it, files and database (it is the newest change, with its own snapshot); Redo makes the Apply again from its record.

## 3. What comes back, and what does not

| Part | Applied? | Why |
|---|---|---|
| `smithable.yml`, `.ux.yml`, `.content.yml`, `.context.yml` | Yes | They are the app's definition. |
| The project's theme files and language files | Yes | The definition names them; without them an old look or text would not validate. |
| `smithable.auth.yml` | Yes, shown apart | Roles and access rules are part of what the app did then. Because it changes who may do what, the confirmation names every role and rule that differs, in its own block, before anything else. |
| Who has access to the project or the app (the people file, invitations, accounts) | **No** | A person removed since then must not come back by a restore. |
| Records (the database's rows), uploaded files | **No** | They are today's. The copy shown in the old-version view has the data from then; applying never takes it. |
| `src/custom/**` | **No** | Owner's code, outside what operations write. If the version's spec names custom code that is not there now, validation says so and the Apply is refused. |
| Secrets, settings of the environment, the published app | **No** | Apply changes the project. Publishing is its own step, as after any change. |

A file the version did not have and the project has now is removed by the change (the plan carries it as absent), so the result is the version's definition and nothing left over.

## 4. When it is refused

Each refusal changes nothing, names its reason in a sentence a person can act on, and leaves the version in the list with Apply unavailable.

1. **The project changed while the version was being looked at.** The request carries the revision the person saw; a different one now is refused with "The app changed while you were looking. See the latest change, then apply again." (the existing expected-revision check).
2. **The version does not pass today's validation.** The files are checked by the current validators before anything is written. What fails is refused, with the validator's words. The spec has one grammar version today and no upgrade steps; when a second version comes, its upgrade step runs on the version's files before the check, and that step is designed with that version, not here.
3. **Records would be lost.** The migration from today's shape to the version's shape is computed first. If it drops a column or a table that holds values, Studio refuses and lists the fields: "This version has no place for: Instructor · phone (41 values)." The command line asks first and takes `--yes`, as it does for every change that loses data. A field that the version requires and today's records lack follows the existing rule for a new required field.
4. **Uncommitted edits in the project**, or a project without history: the existing refusals.
5. **The commit cannot be read** (a history that was cut): "This version is no longer stored."

Applying the version that is already current is not offered.

## 5. The record

The commit is recorded as an operation of its own, `restoreVersion`, with the version's commit as its only argument, so the trace, Redo and assistants read it like any other. Its subject says what a person did: `Applied the version from 12 November, 14:02 (after "Instructors: added a phone")`.

`restoreVersion` is a host operation like `undo`: it needs the history, which only a host package reads. Core gains nothing but its name and description in the registry, so that the operations page and the MCP tools list it. The MCP tool and `smithable restore <change>` take the same checks; `--check` says whether it would be refused and why, and changes nothing.

`FilesPlan` grows from the five editable files to these plus the theme and language files, each as its text or as absent.

## 6. In Studio

The history list and the isolated viewer are the seventh build. This build adds, to the viewer's bar and to the entry in the list, **Apply this version**:

1. A click asks for the check first. Studio shows what Apply would do in the person's words: the changes it takes back and the ones it brings back (from the operations' own descriptions), the access block of §3 if roles or rules differ, and "Your records stay as they are." or the refusal of §4.
2. Confirm makes the change. The old-version tab closes, the preview shows the app as it now is, and the list has a new first entry.
3. Undo is offered at once, as after any change.

Where looking at old versions is not offered (the hosted service today), Apply is not offered either: a person should not apply what they could not see. The command line and MCP have it everywhere.

## 7. What must hold, and its tests

1. A → B → undo B → C → apply B: the files equal B's for every applied part of §3; B's and C's commits are still in the history; reopening the project shows the same.
2. Records made after B are present after the Apply, with values in every field both shapes have.
3. Undo after the Apply gives the files and the database of just before it; Redo gives the Apply again.
4. A person removed from the project after B is still removed after applying B.
5. Each refusal of §4 leaves the working tree, the database and the history byte-identical.
6. Applying a version generated by an older kit produces today's generated files for that definition (the same bytes as making that definition fresh), which is rule 6 of the project: identical input, identical output.
7. A second Apply request with a stale revision is refused; two at once make one change.

## 8. Not in this note

Applying a version to the published app directly, applying only a part of a version (one page, the look alone: Undo of a single change and the look gallery cover those), and bringing back records from a snapshot (that is restore from backup, its own flow).
