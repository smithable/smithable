# As built

How each part was built, what was measured and what was tried and dropped. [ARCHITECTURE.md](ARCHITECTURE.md) keeps the decisions; this keeps the history behind them.

## Smith and Ask, measured (2026-11-13)

What the first measured rounds found (scripts/bench-smith.mjs, scripts/bench-ask-rights.mjs, scripts/bench-first-builds.mjs; the scoreboard is docs/benchmarks/smith-scoreboard.md):

- **Smith on 275 labelled requests**, on Mistral before the switch to Claude: the small model alone 139 right, small then better 155. The better model bought four changes, six data requests and one two-things request more, at about five times the cost per change. Questions about the docs (2 to 3 of 28) and about the app (12 of 38) were low on both, which pointed at what Smith reads, not the model's size; Smith now finds the docs' and the app's parts for every request (#1153, #1161). The first run lost 119 of 275 requests to the provider's rate limit: the bench now asks again after a wait and keeps its rows as they come.
- **Ask's rights**: 35 of 35 cases held, 24 through an app's tools as a role or a visitor and 11 as a signed-in person through the app's own Ask, including an instruction planted in a record (read, named and ignored). Each case is judged on the tools' results and the records afterwards, never on the model's words.
- **First builds without a model**: all 27 labelled descriptions built from the starter `new` names; 29 % of the must-haves met, as a starter rarely fits a description, 34 % once the suggestion weighed who the app is for (#1164).
- **An evolution change by Smith** (a page for staff, asked in Studio): every record kept and the undo exact, but the page was not given to staff, and it duplicated a staff page the starter already had; who a new page is for is now checked by rule (#1157).


**Implemented so far (M10):** `theme` (preset, brand colour and font, density), per page `icon`, `table.columns`, `table.below` (a second field under a column) and `form.fieldOrder`, and `tones` for choice values (success, warning, danger; shown as the badge colour), with `setTheme`, `setColumns`, `setFieldOrder`, `setTone`, `setIcon` and `setBelow` (a page without an icon gets one suggested by its model's name); renaming or removing a field updates it, as it does `smithable.content.yml`. The adapter generates `src/theme.css` from the delivered design system ([design/delivery/](design/delivery/README.md)): each preset's shadcn/ui colour tokens in OKLCH for light and dark (`theme-presets.ts`, copied from its `themes.css`), its font, radius and card shadow, and the density's control height, row height and padding, which the kit uses as Tailwind utilities (`h-control`, `h-row`, `px-cell`, `p-card`; touch screens always get 44 px controls). A brand colour goes through the delivered brand-input rules (`brand.ts`: it replaces primary, ring, accent and chart-1, capped in chroma per preset and moved in lightness until text on it has at least 4.5:1), tested against the design's 24 worked examples. Fonts (Inter, Nunito Sans, Source Sans 3) are self-hosted Fontsource packages (OFL) added to the app's `package.json`; the kit's icons are lucide-react, as in shadcn/ui. The shell is a sidebar from 1024 px and, below that, a header whose menu opens the same navigation in a native modal `<dialog>` (focus trap, Escape and focus return come from the browser); below 768 px tables become record cards (name, contact, status, key amount). A related record is chosen in a searchable combobox (the WAI-ARIA pattern: type to filter, arrow keys, Enter, Escape), and deleting asks in a native modal `<dialog>` that names the record and starts on Cancel. `pnpm test:apps` checks every example's theme for contrast (axe-core, WCAG 2 AA) in light and dark, on desktop and a phone.

## M12: Smithable's own AI

**Implemented so far (M12):** `@smithable/ai` (an engine package: runs in the browser and Node, I/O only through `fetch`) with the provider interface, an OpenAI-compatible provider, the policy (`route` orders allowed providers cheapest tier first) and `proposeChange`. It sends the semantic slice from `buildContext` plus each operation's argument signature, asks for JSON constrained to an answer schema (operations, a question, or "none"), dry-runs the operations with `applyOperation`, gives the model one repair attempt with the error, then escalates. `smithable ask` shows the proposal and applies it after confirmation through `runOperation`. Studio's Describe tab (and an edit of "Your app") applies a proposal at once when it loses no data, since Undo (or Ctrl+Z) takes it back, and says what it did; a proposal that deletes data is shown first and waits for Apply, and each of its steps whose Manual form can hold all its values can open there, filled in, to be adjusted by hand; each commit carries a `Smithable-AI` trailer (tier, model, tokens, cost) that the change trace reads. Providers come from environment variables ([ai.md](ai.md)); the Claude Code provider (in the CLI, since it starts a process) runs `claude -p` with no tools, no MCP servers and an empty working directory, and reports its cost in dollars (usage carries a currency). Tests use a scripted stand-in model over HTTP (`scripts/fake-model.mjs`). Starting from a sentence (§9.8): `closestStarter` picks the starter by shared words, `draftProject` has the strongest allowed model adapt its spec files (guided by the spec's JSON Schema) and validates them with `checkSpecFiles`, sending errors back once; `smithable new --describe` shows the summary and creates the app after confirmation. Still to do: embeddings for shortlisting.

## M13: custom code

**Implemented so far (M13):** custom queries (`queries:` in the spec, a generated result type, a one-time stub in `src/custom/queries/` that returns every readable record, dashboard tiles with `query:`), and a coder for custom code: `smithable code <concept>` or `smithable ask` after a proposal that adds a query. The coder (Claude Code headless, allowed to edit only `src/custom/**` and to run the type check; or any command) is not trusted: Smithable lists every changed file (with `git status -uall`; since the 2026-09-28 review also ignored files and the Git hooks), undoes everything if one is outside `src/custom/`, then requires the type check and tests to pass, and commits with the usage trailer. Claude Code runs with `--permission-mode dontAsk` (only pre-approved actions) and path-scoped rules for reading too (`Read(./**)`); in testing, `acceptEdits` let it write outside its area, and plain `Read` let it read the Smithable repository, so the host's own check stays the real guard.

## M13: Teach Smithable

**Implemented so far (M13, Teach Smithable):** project plugins as in §5.1, in their simplest form: `smithable/plugins/<key>/plugin.mjs` (one ES module, loaded by the CLI with `require`, passed to `validateSpec`, `applyOperation` and `generateApp`), declared in `smithable.context.yml`. `expand` merges ordinary spec into the document before the sections parse (so every built-in generator, migration and access rule applies), and `generate` may write only `src/generated/plugins/<key>/**`. `smithable teach <key>` runs the checked coder with that folder as its area; the coder runs only the type check, and Smithable validates the plugin by regenerating afterwards (running the plugin, or the tests, is Smithable's job, not the coder's). Studio's engine in the tab loads the same modules: Studio's server lists the declared plugins in the project it sends and serves each one at `/api/plugins/<key>.mjs`, and the tab imports them (keyed by their modification time, so a changed plugin loads again) before it validates anything. Not yet: plugin operations and summaries; long-running processes keep the plugin version they loaded first.

## M14: the first Release run

`smithable update --security` regenerates with the current stack profile, whose security overrides Smithable keeps in the project's `pnpm-workspace.yaml` (pnpm reads overrides only there; retired ones are removed, the rest of the file is left alone), and keeps the result only when the normal checks pass. What the first Release run found, and the fixes: an old esbuild (an override to 0.28.2), 80+ Debian vulnerabilities in `node:24-slim` (the image now runs on `distroless/nodejs24-debian13:nonroot`), missing security headers (a production `server.mjs` gives every response nosniff, framing, referrer, permissions and cross-origin headers; pages get a Content Security Policy with a per-request nonce, TanStack Start's `ssr.nonce`), and Smithable's own `.smithable/files.json`, whose path-and-hash pairs looked like API keys to Gitleaks (now `{ path, sha256 }` entries). `pnpm test:apps` checks that production pages carry the headers and that the policy blocks nothing a page needs.

## M15: the hosted beta

**Publishing and data in the hosted beta (M15):** publishing checks the project's committed state (type check, tests) and builds it in a gVisor sandbox, then assembles the image with a runtime-only Dockerfile of `COPY` lines, so no project code runs outside a sandbox. `node_modules` is the first layer after the base image, so apps with the same dependencies share it. Apps run under gVisor with memory, CPU and process caps and their own data volume, on `a-<id>.<domain>` or the tester's own domain (an A record to the service; the certificate is made on the first visit), sleep when idle and wake on the next request. Backups: a project's directory with its Git history and a `VACUUM INTO` copy of its development database when its workspace stops; an app's data when it sleeps and nightly; the service's own database hourly; all to a versioned S3 bucket, with a tested restore for each. Containers never get the host's cloud credentials (metadata hop limit 1 and a firewall rule): the host copies backups to S3, and the model key reaches only the service's AI gateway, which gives each workspace a project token, meters its cost against the owner's monthly allowance and calls the EU-hosted model. Dependencies are prepared by content: projects whose dependency files hash the same (a few variants per stack profile) share one installed copy, made once in the sandbox as an ordinary project at `/opt/deps` (with pnpm's store and metadata cache, so pnpm's supply-chain check needs no registry) and kept as an image layer; each workspace gets its own copy-on-write view, so nothing is shared writably. A matching project uses `/opt/deps/node_modules/.pnpm` as its virtual store: its own `node_modules` is about 10 MB of links, and a package's usual lookups up the directory tree reach `/opt/deps/node_modules`, which has the same direct dependencies. A project whose dependencies differ gets a normal install. The starters' sets are prepared at each release. On AWS a new project's Studio opens in 13 s instead of about 30, and its preview in 27 s instead of 41. pnpm's global virtual store was tried and dropped: its stricter layout hides packages that TypeScript and some tools find only through hoisting, so a fresh app failed its type check. Smithable also runs the app's tools from `node_modules/.bin` rather than through `pnpm exec`, which costs 1.5 s per call in a sandbox. A warm pool keeps one workspace per starter waiting, created with its final project id (so its addresses, AI token and certificates are right in advance), Studio started and the preview warmed; a new app from a starter, or the public demo, claims it, the owner's name goes into its Git settings, and the pool refills in the background. A new app then opens Studio in 1.3 s and its preview in 1.8 s. Waiting workspaces are never stopped as idle nor backed up, and each release replaces them. The migration for an operation's schema change is made in Smithable's own process with the app's own drizzle-kit through its programmatic API (the same SQL and snapshot as its command line, which a test compares; the same files, so drizzle-kit carries on after detach and finds nothing to migrate), with the command line as the fallback; the operation pipeline is asynchronous for it. An operation runs only the tools its change needs: the install only when packages changed, drizzle-kit and the migration only when the schema changed, and the migration is applied in Studio's own process with the app's own Drizzle and SQLite driver (0.3 s instead of 1.9 s for a separate process). Hosted, a field change then takes about 5 s and an access change 3.7 s (both 6 to 8 s before). The route tree is also written in-process, with the app's own router generator (what `tsr generate` runs), in well under 0.1 s. Why skipping it had broken the preview turned out to be timing: when an operation finished quickly, Studio reloaded the preview while TanStack Start was still rebuilding, and that request hung; the separate processes had hidden the race. Studio now answers the operation at once and reloads the preview a moment later, once the preview editor plugin's `/__smithable/settled` says the dev server's watcher is quiet. The migration imports the app's schema with Node's own type stripping and a fresh query string, so drizzle-orm stays loaded between operations (milliseconds instead of a quarter of a second, seconds in a sandbox), and Studio loads the operation tools in the background as soon as it starts, so a pool workspace has them ready before anyone claims it. Measured on the beta (2026-09-28, a new CRM from the pool): the first field change 2.4 s, an access change 1.3 s, the next field change 1.4 s (9.1, 4.3 and 7.5 s that morning).

## Studio: the summary and its editing

The summary lists a model's fields one per line under "Customers have:", gives pages and sign-in their own headings, and puts formulas in words (`formulaInWords`: "the quantity times the unit price", "0 if … , otherwise 5"). Builder speaks the summary's language everywhere: the change list, the status line, proposals and the forms' previews word each change with `describeChange` ("Customers: added a website (a web address)", from the operation each commit records in its `Smithable-Op` trailer), and the field panel shows a field as the summary lists it; Studio mode keeps the operations' own descriptions and the spec's shorthand. "Your app" is a map to the app's parts (docs/design/studio-v2.md §5): a click on a part opens its properties under it, the same panel Code mode's details show, where each control is an operation; the groups have add buttons that open the Change tab's forms filled in. "In my words" rewords a part for the session only (in the tab's `sessionStorage`) and never changes the app; a change that touches the part brings the generated sentences back, marked "updated"; Ctrl+Z (Cmd+Z) outside a text field undoes the last change, in Studio and in the preview (whose editor script passes it on); the spec editor saves through the `editSpec` operation, so an edit gets the same checks, migration, checkpoint and undo as any operation. The change trace is read from the operations' commits (`Smithable-Duration` records how long each took).

## M16: the look fixes

Johan set the booking starter beside a company site (el.ax) and found five visible differences; none needed a new construct.
- **The cover hero:** `layout: cover` puts the picture across the width under a wash of the theme's primary, with the title and line in the primary's foreground color. On phones the wash is near-solid behind the text block, because the light end of the gradient left the text on the picture.
- **Shortcuts:** up to four page references, drawn as round icons over the hero's lower edge, with each page's title as its label. A shortcut to a page visitors cannot open warns, but only when the landing page itself is public; a button into the app is a deliberate door to sign-in.
- **Pictures on cards:** a card is 3:2 with `object-cover`. The placeholder (the theme's muted tone with the model's icon) appears only when the model has a picture field; a model without one keeps text cards, which otherwise read as unfinished.
- **The site frame:** a header menu of the public pages in the spec's order, collapsing to a button on narrow screens; a footer in columns (the contact section's details, the pages, and a legal line), keeping the one-line footer when there is nothing to show. A public page that is not a landing page (the schedule) gives a visitor the site's header and footer, and someone signed in the app's shell.
- **Scale and rhythm:** larger hero and section titles and less vertical air, which changed every app's output once on purpose. Each preset now has its own shape from the delivered tokens: radius, card borders, shadows (playful's tinted with the primary), heading weight and tracking, and density (corporate is compact unless the ux file says otherwise).

## M16: sample data

Starter records are project files, `samples/<Model>.yml`, rather than spec grammar. They are data, not behavior: changing them changes no generated code, so they need no §2.4 questions and stay out of the spec's schema, and an owner edits them like any file. A reference names a record by its title, and only against the referenced model's own file; without one, the record's number is used.
- **Errors and warnings:** a wrong value or a reference to a record that isn't there is an error with its position, since seeding it would fail or mislead. A key for a field or model that no longer exists only warns and is left out, because a rename or removal must not block regeneration. Operations also rename or drop those keys themselves (#98), after main's tests showed `renameField` leaving `notes:` behind.
- **The starters' tests:** the generated rows' names and order numbers that the tests click on were kept in the CRM's samples. Everything else is two real sentences per record.
- `new --no-sample-data` leaves the folder and the seed out.

## The security review of 2026-10-04

What a review of the stack and one local test of a generated app found, and what was built for each:

- **The scanners were days behind.** Six advisories for the web framework, the sign-in library and the mail library were on their projects' own pages and in neither OSV nor GitHub's reviewed list four days later. `smithable security` now reads each named package's own advisory list too, and CI checks the stack's pins daily (ARCHITECTURE §12).
- **Server functions answered other sites.** A start file of our own had switched the framework's cross-site check off; it is on, for server functions only.
- **The dev server handed out the app's data folder**, the database and the sign-in codes with it, to whoever could reach it. It is denied.
- **A public read told who owns a record.** The owner's id now reaches only the owner and roles that read every record, in a record's lists of related records too.
- **Containers on the host could reach the internet directly**, past the outgoing proxy (the hosted service; closed there, with a release check).
- The rest of the test, which a safety filter kept one session from running, became named checks in the gate (`security: …` in `test-apps`), and a ceiling on request bodies and on adding up computed fields.

## CI minutes, 2026-10-05

GitHub Actions stopped starting jobs: its minutes had run out. Since then a pull request of plain documents alone starts no run and is merged by `scripts/merge-green.sh` itself after a scan for secrets; a push to main starts no run; and a pull request is not run again for being behind main. Main's full check, twice a day, is where two changes that only clash together now show.

## M16: the API and the tools for assistants

An app offers nothing to programs unless its auth file says so, in one `api` block beside `public` (#209). An administrator makes a key on the users page with a name, a role and an optional end date; it is shown once, stored as a SHA-256 hash, and the audit log records that it was made or revoked, never the key (#225). A key is a role, not a person, so what it creates has no owner. The routes under `/api/v1` and their OpenAPI description come from the same offer (#230), and a call without a key is the visitor, with the visitor's write limit (#260, #271).

The same offer is served as tools at `/mcp` when the auth file says `api: { assistants: true }`: a stateless JSON-RPC endpoint in the Model Context Protocol's form, through the same data functions, keys, limiter and refusals as the API (#235). Deleting is offered only when the spec says so, since an assistant can be steered by the text of a record it reads. The first version had a tool per model and verb. It was replaced by seven general tools (find, measure, read, add, change, run, describe), with filters, search, sort and sums worked out by the app (#280), after a bench on three models: tool results went from about 650 tokens a question to about 50, the tokens sent per question fell by a fifth to a third, right answers rose on two of the models and stayed within two misses on the third, and no answer was wrong any more because a model had added up rows itself (#295, `docs/benchmarks/bench-ask-seven-tools.md`). The same seven tools are what Ask uses inside the app.

## M16: Ask's answers checked against its tools

The bench's wrong answers were of a few kinds: a "none" when a result was not empty, a change claimed that was never proposed, a number that was in no result, a kind of record named when no tool had returned anything ([design/ask-checks.md](design/ask-checks.md)). The kit's `grounded.ts` reads the model's final words for each of these without a model; an answer that fails goes back to the same model once with the reason, then once more marked so the hosted gateway can hand it to a better model, and if it still fails it is shown muted beside the results as unconfirmed (#621). The first measurement found false positives, which were taken out (#625), and three tool rules followed, so a tool's answer leaves no room: an empty result says why, a shared top value is said, and a zero is never answered quietly (#620, #628, #630). A grounded answer costs no extra call.

## M16: outgoing calls, push and texts

Everything an app sends goes through an outbox row written in the change's own transaction, so a change never waits for another system and a rolled-back change sends nothing ([design/integrations.md](design/integrations.md) §4). A failed delivery is retried with growing pauses for a day, and each call carries an `Idempotency-Key` that is the same on every try (#568).

**The guard.** A call to another service is made through the kit's `call.server.ts`. The name is looked up once, every address it returns is checked against private and local networks (IPv6 included), and the connection goes to the checked address, with the Host header and TLS still using the name; redirects are an answer, never followed (#555). The first version checked one lookup and connected with another; that is fixed. A hosted app reaches the internet only through the service's egress proxy, which allows only the addresses the owner named (§6.1). Behind it the kit does not resolve the name itself and lets the proxy check the destination; the proxy's refusals arrive as `fetch` errors rather than statuses, so the kit reads them: a stale credential is tried again in a minute, a used-up day in ten minutes, and an address not connected tells the owner to connect it (#568). A test runs the status app's call through a stand-in proxy (#571).

**Push** is one kit file on Node's own crypto, with no push package: the message is encrypted for each browser (RFC 8291) and signed for the push service (RFC 8292), and a test checks it byte for byte against the RFC's own example (#1093). Without keys in the settings the app makes a pair at its first start and keeps it in its database, so a backup keeps everyone's subscriptions. At each send the outbox checks again that the person still wants the notice and may read the record.

**Texts** go through the owner's SMS provider, or into a folder in development as mail does (#1096). A number on a record is texted only from a signed-in person's change, never a visitor's, who could have typed anyone's number. A text is marked unknown before the provider is asked; with no answer it stays unknown and is never sent again by itself, since a text sent twice cannot be taken back. **Live notices** are server-sent events to whoever has the app open, sent only when the mail row they announce is really there after the transaction, so a rolled-back change is never announced (#1082).

## M16: timers

A timer says what the app does on a clock or at a time relative to a record's date ([design/timed-actions.md](design/timed-actions.md), #766). The generated `timers.server.ts` ticks every minute and works out what is due at the tick, never scheduling ahead, so a record whose date moved is simply found at its new time (#770). A table `timer_runs` takes each run before it acts (timer, record, due time as written), so two processes or a restart never run the same thing twice. A missed window is caught up by kind: a record timer's due records run late within a day and older ones are counted in Activity, since yesterday's reminder helps no one; a clock timer runs once for the latest time due, however long the app was down. A timer's first sighting is written without a run, so a new timer never runs for the past. The kit's `clock.ts` handles the clock changes: a minute the spring change skips runs at the next minute, and the autumn repeat runs once. A run acts as the app (`Viewer.system`), keeps the record's owner, and is named in Activity as the timer.

A review of the first version found that two overlapping ticks could both retry a failed run, and that a crash mid-run silenced a record's timer for good. A run is now taken back only by an update one tick can win, either when it failed or when it has been running for ten minutes, each below three tries (#774). In development timers do not fire on their own; `smithable timers run <name> [--at <time>]` runs one, and the starters' tests use it (#770).

## M16: files and their review

A record takes a new file only with the receipt its upload returned (#559). Uploads never saved are swept away after a day, the file too unless a record of its model uses it, and `UPLOADS_MAX_BYTES` bounds an app's storage, refusing an upload before its body is read (#563).

Files reviewed before others see them ([design/file-review.md](design/file-review.md)) live in a `file_reviews` table, generated only when a model has `review` (#466, #468). Whether the field is required decides what is held: a required reviewed file holds the whole record, which is then out of every read (lists, search, the API, the assistant's tools) for all but its owner and the reviewers, through the same `readable()` filter as every other rule; an optional one holds only the file, which answers 404 to others. A file with no row is not held, so sample data and a reviewer's own uploads need nothing. Rejecting removes the file from disk unless another record shows it. The app bundles no virus scanner: files are never run by the app, pictures are re-encoded in the browser and documents are served as attachments under a sandbox policy. What exists is a hook: with `SCAN_URL` set, the bytes go there before anything is stored, and any answer but OK refuses the upload.

## M16: sample users

Sample users act in the preview as a person at the keyboard would ([design/sample-users.md](design/sample-users.md)). What each may do is read from the spec and the auth file by rule, in core, without a model: a list of move shapes with their slots, filled with values by the same rules as the sample data (#882). The app has one door for them, generated into every build but answering only in a development build (or a demo, without the clock) and only to the secret the host gives it: one call lists the moves open to a user now against the data, another performs one through the same server functions the pages call, so grants, validation, Activity, mail and timers hold as for a person; a third shifts the development build's "now", so "a week later" is a call (#888). Sample users exist only in the development database, and nothing is added to the schema.

The host runs the loop, never the app (#896). A model, when one is used, only picks a move from the list and fills its text slots; anything else is dropped and the next move is drawn from the person's memory. Every turn is written to the run's log, and the memory, the coverage table and the feed are rendered from it, so a run with a model can be replayed. A sensible run weighs moves by what the person did last; a try-everything run walks each move's variants, valid ones and ones the spec's own rules must refuse, untried first, and judges each by its mark (#907, #910). The door's secret can also be given by whoever starts the preview, so a tester outside Studio drives the same door (#1005).

## M16: payments

A record is paid on the provider's own page and recorded as paid only by the provider's verified word ([design/payments.md](design/payments.md)). A model paid when it is created is written held: it shows nowhere and tells nobody until the word comes, a hold timer releases what nobody paid for, and the amount is read on the server from the record in its own transaction (#1103). The Payment's status moves only as core's allowed moves say, each provider event id is taken once, and money that does not match is recorded and the held record released. Providers sit behind one kit interface (create a checkout, verify an event, refund, close). Stripe and Mollie are modules over their plain HTTPS APIs, with no SDK in the app, through the kit's guarded call (#1106): Stripe's events are verified by their signature, while Mollie's carry only an id, so the app asks Mollie with its own key what happened and acts on that answer. Before a held record is released the timer closes the open checkout at the provider and asks again, since it may have been paid in between.

The `fake` provider is a page of the app itself with Approve and Decline that posts a signed event back, as a provider would, so the tests, the preview and a hosted staging copy need no network and no account (#1103, #1108). It can never complete a real payment: its routes answer 404 unless it is the provider in use, and an event is applied only to a Payment made by the same provider (#1108).

## M16: a first build from a website

`smithable new --from <url>` reads a bounded site: twelve pages, depth two, sixty seconds and 8 MiB, the same host and its www twin, every address and redirect checked against robots (#1035). The reader turns it into a versioned bundle of facts (the business's name, contacts, navigation, forms) and the draft is made from those facts, never from the site's prose (#1034, #1035). After generation the visible texts are compared with the whole source; ten words in a row in common get one rewrite from the facts, and a second match neutral wording. Before any model sees the facts, people, street addresses, phone numbers and mailboxes are replaced with sample values by a pass without a model, and the generated files and model requests are checked against what was found (#1040). A website's pictures are interpreted from their text only, and an original photograph needs review before it is used, with a row in the release checks (#1035). The first build itself is a durable job that resumes after a restart and records what it assumed (#1034).
