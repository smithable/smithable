# What a starter costs, 2026-10-07 against 2026-09-30

Johan's consolidation item 4: what the last weeks of features cost a generated app's visitors and hosts, and the gate that checks them. Measured with `node scripts/measure-app.mjs [--engine <checkout>] [--image] [--gate]`, which makes each starter with that engine's `smithable new`, builds it for production, and prints the table; run it again to compare.

**The baseline.** The repository starts on 2026-09-26, so there is no main of a month ago. The baseline is main at the end of 2026-09-30 (`75c7604f`), the earliest with four of today's seven starters (crm, booking, invoicing, records); marketplace, status and api have today's numbers only. Today is main at `4c518d47`.

**What is measured**, per starter, on this machine (WSL, eight cores, other sessions' work running beside it, so read the times as ±10 %):

- **First page:** where a visitor lands on `/` (an invite-only app sends them to sign-in).
- **JS and CSS:** what that page loads, gzipped here (level 6) the same way for both engines, so the numbers compare even if a server compresses differently.
- **Cold start:** the production server, freshly started, until `/health` answers 200.
- **To hydrated:** from asking for the first page on that cold server until React has taken over the document (its keys on `<body>`), in a fresh browser at 390 × 844.
- **Image:** the app's own Dockerfile, built (`docker image inspect`, uncompressed).
- **Kit files:** the files of `src/kit` the app gets, and their source size: the ledger of which parts each starter carries.
- **Gate:** `pnpm check` under `scripts/gate.sh`, from its turn to its end.

## What doubled, and where it went

Nothing a visitor or a host pays for doubled. The first page's JavaScript grew 4–6 % (9–14 kB gzip), its CSS 1.3–1.8 kB, the image 1–5 MB of about 110, the cold start by a tenth of a second, the time to hydrated by 0.02–0.07 s.

Two things did double:

1. **The kit's source per app**, from 17–25 files (82–137 kB) to 32–44 (172–273 kB). Most of the new parts run on the server or only when used, which is why the shipped JavaScript hardly moved: the audit log, the outbox and the request log (`audit.server`, `outgoing.server`, `log.server`, `trace.server`, `address.server`), the CSV export (`csv`), the trash (`Trash`), consent (`Consent`, `consent`), the API and tools (`api.server`, `mcp.server`, `tools`, `where`), and the words (`words`, one language per app, 19 kB of source). The client parts that grew most are the form and the table (ModelForm 14 → 19 kB, ModelTable 8 → 19 kB: phone cards, selection, paging, trash, CSV) and the landing page (28 → 40 kB). A maker reading their app's code meets twice as much kit; nobody's browser downloads it.
2. **The gate**, 317 → 669 s. It checks more than twice as much: seven example apps instead of four (test-apps runs them side by side, but every example adds its build, smoke tests and browser flows to a machine that is already full), test-apps itself from 2,039 to 5,395 lines of flows, test-studio from 36 steps to 58, and the unit tests from 66 files to 108 (those take 10 s). The time per thing checked is about what it was; there is more of it.

## Where the bytes are now

The first page of every starter is about 250 kB of JavaScript (gzip), and three files carry most of it:

- `index` (104–122 kB): React, the router and the app shell. It grew by 2–12 kB this fortnight.
- `schema` (61 kB) and `schemas` (38–71 kB): both are zod, the validation library (its classic API and its core), not the app's own schemas. The entry imports them, so every first page loads them, a sign-in page and a landing page included; they were there on 2026-09-30 too. The likely cause: routes check their address with `validateSearch: z.object(…)` (the sign-in page, the lists, the new forms), and a route's options are part of the route tree that every page loads, unlike its component, which is split off. The better-auth client may use zod as well; that is to be checked first.

## Trims, proposed (nothing built)

1. **Keep zod out of the entry**: done in backlog 47, below.
2. **The landing page's kit file** (40 kB of source, the largest): its section kinds in their own files, so an app loads only the sections it uses (a status page has no FAQ, invoicing no calendar).
3. **ModelTable** (19 kB of source): its selection bar, paging and CSV export as parts loaded by the pages that offer them (a visitor's catalogue needs none).
4. **The gate:** run test-apps' browser flows for the examples a change touches (an adapter change: all; a Studio change: none, as today; a kit file: the examples that get it, from the ledger above), and keep the full run for CI's check of main twice a day. That would bring most local gates back near five minutes; the risk is a change that breaks an example it was not expected to touch, which main's full check catches within half a day.

None of these changes what an app does; each is the adapter's to do, measured again with this script.

## After the first trim (backlog 47)

Zod came into every first page four ways, not one: the routes' `validateSearch: z.object(…)` (in the route tree); the sign-in page's and the root's own server functions' inputs; the models' form schemas, built at the top of the model modules that the list loaders import; and a custom action's input schema, in an action module the bundler places in the entry because three of a page's chunks share it. The better-auth client does not use it. The trim:

- An address is checked by hand (`src/kit/params.ts`: `text`, `count`, `shaped`, `oneOf`, each value optional as zod's were), and so are the sign-in page's and the root's few server inputs.
- A route's loader is split off the route tree like its component (`vite.config.ts`, TanStack's `codeSplittingOptions`).
- A model's form schema is its own module, `src/generated/<model>.schema.ts`, and a custom action's input `src/generated/actions/<action>.input.ts`: forms, the API and the server load them, a list or a landing page does not.
