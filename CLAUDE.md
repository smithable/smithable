# Smithable

Local-first, manifest-driven app builder. Read `docs/VISION.md` for the why, `docs/ARCHITECTURE.md` for decisions, and `docs/ROADMAP.md` for the current milestone. Architecture changes must update `docs/ARCHITECTURE.md` in the same change.

## Development

- Node 24 (`.node-version`, managed with fnm) and pnpm (version pinned in `package.json`).
- `pnpm install`, then:
  - `pnpm build`: `tsc -b` over the project references in `tsconfig.json`.
  - `pnpm test`: Vitest, tests live next to the code as `src/**/*.test.ts`.
  - `pnpm lint`: Biome lint and format check, and `scripts/kit-words.mjs` (the app kit writes no visible English of its own: its words are in `words/<language>.ts`). `pnpm fix` applies Biome's fixes.
  - `pnpm test:apps`: generates every example in `examples/` into a temporary directory, then type-checks, builds, serves and regenerates it, one process per example, at most half the cores at once (`TEST_APPS_CONCURRENCY`). `pnpm test:apps:one <example>` runs one.
  - `pnpm test:studio`: runs `smithable studio` on a new CRM and makes the M3–M5 changes in both modes in a real browser.
  - `pnpm test:container` (needs Docker): builds the CRM image and checks that data survives replacing the container. Not part of `check`.
  - `pnpm test:fresh` (needs Docker and the network): the README's first steps in a container with only Node and Git, nothing configured: install, build, a new app, a change from the command line and from Studio, the preview answering. Run it before a release and after a change to `new`, the Git handling or the dependencies. Not part of `check`.
  - `pnpm test:deploy` (needs Docker): deploys the CRM after the Release checks, backs it up to an S3-compatible bucket (SeaweedFS), destroys it and restores it into a fresh container; also the Compose export and a folder backup. Not part of `check`.
  - `node scripts/bench-m3.mjs`: the M3 mini-benchmark (Smithable operations vs Claude Code headless on the same tasks). Uses the user's Claude usage; ask before running. Writes `docs/benchmarks/m3-mini.md`.
  - `node scripts/bench-m7.mjs [S] [A] [B] [M]`: the M7 benchmark (seven tasks by Smithable operations, plain Claude Code, Claude Code with MCP, and `smithable ask` with the configured model). S is free; A and B use the user's Claude usage and M the configured model's, so ask before running them. Writes `docs/benchmarks/m7.md` (or `m7-<setups>.md`).
  - `node scripts/bench-m12.mjs`: M12 first builds: ten descriptions through `smithable new --describe` with the configured model (see `docs/ai.md`). Ask before running with a paid model. Writes `docs/benchmarks/m12-first-builds-<model>.md`.
  - `node scripts/bench-m6.mjs`: the M6 exit check (Claude Code headless with only the Smithable MCP server). Uses the user's Claude usage; ask before running. Writes `docs/benchmarks/m6-mcp.md`.
  - `node scripts/bench-read.mjs [--trace] [--blind <file>]`: the reader of first descriptions that uses no model (`packages/ai/src/read-description.ts`), against the bench's descriptions and the blind set `docs/benchmarks/read-blind.json`, each with what is right: what it settled, what it asked, what it got wrong. Free. Not part of `check`.
  - `node scripts/stack-advisories.mjs`: the stack profile's pins against their packages' own advisory lists on GitHub (the vulnerability databases list a new hole days later). Exits 1 when a pinned version has a published hole or a list could not be read; also names the pins with a newer patch release. Free; `GITHUB_TOKEN` (or `GH_TOKEN=$(gh auth token)`) lifts GitHub's sixty calls an hour. CI runs it daily (`.github/workflows/stack-advisories.yml`). Not part of `check`.
  - `node scripts/theme-sheet.mjs [preset | themes/<name>.yml …] [--out <dir>]`: the theme sheet. Makes a booking app with every form control, applies each theme through the operation layer, and screenshots the landing page, a list, a form and a dialog in light and dark into one PNG per theme (default `/mnt/c/Users/johan/Pictures/claude/themes/`, port 8402). Without themes it shoots the four presets. Not part of `check`.
  - `node scripts/starter-shots.mjs [starter…] [--copy <dir>]`: the Starters page's pictures. Makes each starter, serves it (port 8403) and takes its two pictures as WebP into `docs/site/starters/`, with a copy in `/mnt/c/Users/johan/Pictures/claude/starters/`. Not part of `check`.
  - `node scripts/hero-pairs.mjs [starter…] [--copy <dir>]`: the landing page's spec-to-app hero (C 21): for each starter a few real lines of its smithable.yml ("Code") or of its plain-language summary ("No code"), and the app they make at the hero's size (1600×1040), into `docs/site/brand/hero/` (`pairs.json` and `<starter>.webp`, served at docs.smithable.ai/brand/hero/) with a copy in `/mnt/c/Users/johan/Pictures/claude/hero/`. Rerun a starter after a change to its spec, summary or look. Not part of `check`.
  - `node scripts/theme-lab-export.mjs`: the theme lab's public mode (theme-lab.md §3): for every starter (booking first, with every control) makes its app, serves it (port 8404) and saves the pages the lab frames as static files with their pictures into `docs/site/theme-lab/frames/<starter>/`, and the Latin faces of the seven fonts once; `node scripts/theme-lab-export.mjs <starter…>` redoes only those, which `pnpm site` serves at docs.smithable.ai/theme-lab/ with the lab built beside them (Save downloads the file). Rerun it after a change to the kit's pages or a starter. Not part of `check`.
  - A theme from a site, for the sheet: `smithable theme --from <url> --name <x>` in a project adds `themes/<x>.yml`, then `node scripts/theme-sheet.mjs <project>/themes/<x>.yml`.
  - `node scripts/theme-candidates.mjs [family…] [--out dir] [--sheets]`: theme candidates by rule (ten families: primary hues, OKLCH lightness ladders for both modes, an accent from a harmony, font, radius, shadow, density). Each is checked like any theme and the unreadable are dropped. Writes the theme files and a thumbnail overview, and with `--sheets` the theme sheet of each survivor. No model, not part of `check`.
  - `node scripts/measure-duplicates.mjs [starter] [--fail] [--json]`: the words a generated app writes as literals in two or more of its files (docs/design/words-once.md): makes the starter in a temporary folder and lists the values found in several files; `--fail` exits 1 when a page's title, the app's name, a role's or a choice's label is written twice, for the adapter's test. Free. Not part of `check`.
  - `pnpm site`: builds docs.smithable.ai into `site/` (the pages in `docs/site/`, the spec reference, the operations page from core's registry, the theme lab's public mode, the JSON Schema, and `search.json`, the index the header's search box (`scripts/docs-search.js`, served as `/search.js`) searches in the browser), failing on a dead link. It builds core and the adapter first by itself, so it runs from a fresh checkout after `pnpm install`. smithable-cloud's Docs workflow publishes it, with `SITE_PRERELEASE=1` (every page `noindex`) until the public release.
  - `pnpm check`: lint + build + test + site + test:apps + test:studio. This is the gate. For an engine change (`packages/`, `apps/`, `examples/`, the scripts `check` runs, the dependencies, the workflow) the local `pnpm check` through `scripts/gate.sh`, exiting 0, is required before the commit (or, when `gate.sh` exits 75 because too many gates are ahead, CI's full check on the pull request, see `gate.sh` below): while the repository is private, CI runs only lint, build, units and site on GitHub's runners for every pull request (the repository variable `FULL_CI` is off), so the example apps and Studio are tested only on this machine: by the local gate, or by CI's full check, which runs on the self-hosted runner here (`docs/ci.md`: one `full` job through `scripts/gate.sh` with `SESSION=ci`, taking its turn in the gate queue). At the public flip `FULL_CI` is turned on and the full check runs for every engine pull request the same way. For the site's pages, the spec reference and tooling scripts `check` does not run, CI's run on the pull request is the gate. Plain documents (design notes in `docs/design/**/*.md`, `docs/benchmarks/`, `docs/research/`, `docs/ARCHITECTURE.md` and its neighbours, the Markdown at the root; the list is in `ci.yml`, and `docs/ai.md` is not on it: it is a page of the site) start no CI run at all, since no job reads them: a pull request of those alone is merged by `scripts/merge-green.sh` itself. A push to main starts no run either; main gets the full check twice a day, which is where two changes that only clash together show, since a pull request is not run again for being behind main.
  - `SESSION=<name> TEST_APPS_PORT=… TEST_STUDIO_PORT=… scripts/gate.sh`: runs `pnpm check` under a machine-wide lock (`/var/lib/smithable-gate/.gate-lock`, shared with the CI runner; `~/repos/.gate-lock` on a machine without that directory), so only one gate runs at a time on this machine, and returns its exit status. Two gates at once saturate the cores and memory. Turns go round the sessions (the one with the fewest turns since the queue was last empty goes first, then by arrival), so queueing several gates gets nobody through sooner; `scripts/gate.sh --queue` shows who runs and who waits. A gate tests the worktree as it is when its turn comes: put several small changes that are ready in one worktree and gate them once, rather than one gate each. A change that touches only Studio's web app (`apps/studio`, `scripts/test-studio.mjs`) and plain documents skips the example apps by itself, since their checks never load it (about four minutes instead of nine). When two or more gates are ahead (the running one counted; about twenty minutes), it does not wait: it exits 75, and CI runs the full check instead. Then run `pnpm lint && pnpm build && pnpm test` in the worktree (no lock needed), commit, push and open the pull request with the label `full-ci`; `scripts/merge-green.sh` merges it when that check has passed. CI's full check runs on this same machine (the self-hosted runner, `docs/ci.md`) and takes a turn in the same gate queue, so the label buys no speed, only a check that runs without a session watching it. `GATE_AHEAD_MAX=99` waits whatever the queue. The checks' waits (a minute for a page in Studio's check, the apps' health) are multiplied by `TEST_PATIENCE`, which the gate sets unless given (2 as a rule, since its own checks load the machine; 3 when the load is already above the cores; `TEST_PATIENCE=1 scripts/gate.sh` to say it), so a slow answer under load is not read as a failure. While the file `/var/lib/smithable-gate/night-cap` exists, a gate started from 23:30 to 07:00 (Mariehamn) runs itself capped, on four cores at the lowest priority, for a quieter machine at night (the runner's service has its own cap, `smithable-runner-cap.timer`); off since 2026-10-18, since a capped gate beside any other load ran out of its one-minute waits. Start a gate in the background and carry on; do not wait for it in the foreground. Single examples, unit tests and the screenshot scripts may run beside a gate.
  - `scripts/merge-green.sh <pr>`: merges a pull request only after every check has passed: arms GitHub's auto-merge so it merges the moment its checks pass, refuses on a failure, conflicts, or when none ran. Conflicts that are only in generated files (`*.gen.ts`, Vitest snapshots) it resolves itself when run from the pull request's own clean worktree: a rebase on main taking the branch's side of them, `pnpm build`, the snapshot's tests with `-u`, a commit and a push, then the new head's checks; any other conflict is refused, rebase it by hand. The one case without a check is a pull request of plain documents alone (above): the script reads the list from main, refuses one that removes a document the site links to, scans its commits for secrets (Gitleaks, needs Docker running), and then merges it as the administrator; do not put a document change and anything else in one pull request if the document is to merge without waiting. One pull request at a time across both repositories and all sessions on the machine: it holds `~/repos/.merge-lock` (the PR, repository, session and time; stale after an hour) while it works, and the others wait. Set `SESSION` to your session's name when you run it. Sessions merge with this and nothing else, since an administrator's merge passes branch protection by: the script's own merge of plain documents is the only one a session makes that way (Johan, 2026-10-05).
  - `pnpm schema`: regenerate `packages/core/schema/smithable.schema.json` after changing a section's schema. A test fails if it is stale.
- App templates live in `packages/adapter-tanstack/templates/` as real files; `pnpm build` embeds them (and the example specs used as starters) via `scripts/embed.mjs`. Generated `*.gen.ts` files are never edited by hand.
- The spec reference is `docs/spec/v0.1.md`. Update it together with any change to the spec grammar.
- The Studio web app (Builder and Studio modes) is `apps/studio` (React + Vite); `pnpm build` builds it, and `smithable studio` serves it.
- New packages go in `packages/<name>` with a `tsconfig.json` extending `tsconfig.base.json`. Add them to the root `tsconfig.json` references.

## Rules when working on Smithable

1. `smithable.yml` is authoritative for functionality. Companions: `smithable.auth.yml` (sign-in, roles), `smithable.ux.yml` (presentation), `smithable.content.yml` (visible text), `smithable.context.yml` (implementation policy; the only one that may name technologies). Never mix their concerns.
2. All semantic changes go through the operation layer. No client writes the manifest files or app code any other way.
3. Deterministic before AI, then the cheapest capable model: local (if available) → Smithable model → frontier. Where a model may run is a setting, the AI policy (`local-only`, `eu-only`, `best-available`; nothing said means the best model configured). EU-only is a guarantee a project or an organization switches on, not the default; smithable.eu, when it exists, is EU-only in infrastructure and AI.
4. **Generated apps must never depend on Smithable packages**, either at runtime or at build time. Generated code follows each library's documented idioms (Drizzle schema, TanStack routes, shadcn/ui). Shared behavior goes in the small, no-magic in-repo app kit.
5. Respect the ownership zones: the compiler never overwrites `src/custom/**` or existing migrations, and neither AI nor humans are expected to edit generated or kit files.
6. Generation must be deterministic and idempotent: identical input produces byte-identical output.
7. Framework knowledge lives in the adapter; the manifest, IR and operations stay framework-neutral.
8. Engine packages (`core`, `adapter-tanstack`, `index`) must run in the browser as well as Node: no Node built-in imports, I/O only through the host interface. Only host packages (`cli`, `daemon`) touch disk, Git or processes.
9. Do not add DSL constructs without passing the five questions in ARCHITECTURE §2.4. Built-in features are internal plugins (ARCHITECTURE §5.1): each spec section registers its schema, operations and generator through the plugin interface.
10. Keep code (Smithable's and generated) concise. No abstraction before a concrete second use.
11. Every change must be possible to undo. Never suppress test or security findings.
12. Build incrementally; each roadmap milestone's exit criteria must be verified by tests.
